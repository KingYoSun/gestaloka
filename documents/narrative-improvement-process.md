# 応答内容から物語の停滞を切り分ける検証手順

移動量の改善では、実際に利用者へ届いた応答を一つずつ読み、原因を特定してから修正する。変更前後の合計値だけで採否を決めない。新しい結果・発見・理解・関係の変化を、以前の提示との差と正確な引用で確認する。

## 制約と完了条件

通常プレイへ、LLM点検による改善専用のループ、候補の生成と採点による選別、点検結果に基づく再生成を追加しない。既存の実行段階の中で、必要な情報の取得・組み立て・指示・出力処理を改善する。開発時に保存記録を検品し、仮説に基づく修正と再検証を繰り返すことは、この制約と区別する。

改修は世界名、職業、人物名、身体の有無、個別の設定や固定の展開メニューへ依存させない。世界ごとの入力や期待する具体的内容は検証資料として持てるが、製品コードや共通プロンプトの分岐にしない。世界の因果とプレイヤーの選択を守り、成功や協力、新しい事件を評価のために強制しない。

着手前に、対象の入力・提示・呼出し・比較元を固定し、次を受入条件として明示する。

1. 対象の全応答について、入力の目的、既知情報との差、問題の箇所と根拠を記録する。
2. 問題に必要な情報が、当時のグラフ、取得結果、実際のモデル入力のどこに存在したかを照合する。未取得を不存在と判断しない。
3. 特定した原因に対応する修正で、対象の停滞・回答不足が解消し、利用者が得る新しい結果や判断材料がどう増えたかを引用付きで示す。内部の無駄が減ったことだけで移動量の改善を達成したとしない。
4. 同じ原因を異なる設定でも確認し、選択の代行、秘密の漏出、根拠のない状態・確かさの変更、回答済み事項の重複を増やしていないことを検証する。
5. 通常プレイへ改善専用のLLM呼出しを追加せず、触った層のテストを通す。実測した費用・時間と限界も記録する。

各反復は、一つの原因仮説と、それを支持または棄却する確認までを範囲とする。反復回数だけで成功・失敗を決めず、未解決の原因を残したまま完了扱いにしない。利用者体験や互換性の変更、資源上限の見直しが必要になった場合は、AGENTS.mdの作業原則に従って判断を求める。

## 応答ごとの分析

あらすじ、各入力への応答、リザルトを時系列で一つずつ記録する。narrative-inspectionの基準と共通の応答判定契約を使い、次の項目を残す。

| 項目           | 照合する内容                                                         |
| -------------- | -------------------------------------------------------------------- |
| 対象           | manifest・シーン・入力・提示・モデル呼出しのID、設定とプロンプトの版 |
| 入力の目的     | 独立した問いや試み、制約、どこまで本人が選んだか                     |
| 既知情報       | 初期提示と当該応答より前の提示。宣言・意図と実行結果を分ける         |
| 実際の応答     | 正確な短い引用、届いた結果、未回答の部分、先送りや復唱               |
| 移動の内容     | 以前と今回の違い、新しい根拠、今後の理解や判断への影響               |
| 内部の根拠     | 当時のグラフ、DB取得結果、各段階の実際の入力・生出力、表示までの加工 |
| 原因と確かめ方 | 下記の分類、失われた箇所、対照となる入力、修正で変わるはずの内容     |

入力が情報を求めている場合、「説明した」「確認した」という行為の描写だけを回答にしない。根拠のある拒否・不知・失敗は結果として扱い、未実施や先送りと区別する。新情報量、重要度、応答性、原則適合は別々に記録し、単一の総合点で相殺しない。

## コンテキストと指示の切り分け

当時の入力を使い、必要な命題を次の順に追う。現在のグラフや修正後のコードから、過去にも同じ情報が渡っていたと推測しない。

1. **グラフの記録・モデル構造**：必要な現実状態、作用経路、所有、観測、解釈を表現でき、参照元から辿れるか。未記録の局所状態を具体化する責務がどこにあるか。記録がないだけで直ちにモデル構造の欠陥としない。
2. **シーン開始時などの取得クエリ**：必要な記録はグラフに存在するが、起点・関係・向き・時点・観測範囲などの条件で取得から漏れていないか。固定スナップショットでクエリを確認する。
3. **コンテキストの組み立て**：取得済みの本文が、背景要約・本人のview・意図形成・行動解決の間で落ちていないか。現実状態を、そのまま本人の知識へ混ぜない。
4. **指示**：必要な情報が実際の入力に存在するのに、指示の曖昧さ、責務の衝突、不要な確認、過度な先送りなどで結果へ使われていないか。根拠となる入力箇所と、関係する指示を対応させる。
5. **出力の処理・保存・提示**：モデルの生出力には必要な内容があり、後段で欠落・要約・状態変更が起きていないか。この場合はプロンプトの問題に置き換えない。

複数の原因がある場合は併記する。根拠が不足する場合は判別保留とし、次に確認する資料を限定する。必要な情報が入力にあったというだけで、指示が原因だと断定せず、世界内で答えられる内容と、生成側が判断すべき内容も確かめる。

## 原因に対応した修正と再検証

指示の問題では、関連する指示と矛盾する箇所を絞って変更し、同じコンテキストと入力で応答を再現する。変更した指示、期待した差、実際の引用、残った問題を記録する。未解決なら、その応答内容から次の仮説を立て直す。プロンプトだけを順番に変えて合計値が上がる案を探さない。

コンテキストの問題では、欠落箇所に応じてシーン開始時のクエリ、組み立て、記録方法を調べる。必要な命題や作用経路を現在のグラフ構造で表せない場合に、モデル構造の変更を検討する。コンテキストにない事実を、プロンプトで知っていることにしない。

修正前後では、問題の応答と、それを生んだ通常の進行経路の両方を確認する。局所的な再現が成功しても、入力が一歩進んだだけなら、その先の利用者向けの結果まで確認する。必要な情報が増えたのか、既知情報を言い換えただけなのかを再び分析する。

同じ原因が現れる別設定と、既に正常な対照例でも確かめる。期待値は人物名や結末を固定せず、要求した結果の到達、根拠、履歴の連続性、本人の選択が守られていることへ置く。

## 記録と採否

各試行の入力・出力・プロンプト・コンテキスト・費用・時間・失敗を保存し、過去の試行を上書きしない。自動検品の失敗と本文の問題を分け、手動検品で補った場合は評価方法の差を明示する。

採否は応答内容と原因仮説の検証結果から決める。件数が増えても復唱や重要でない描写が増えただけなら、その限界を記す。合計値が同じでも、求めた答えが届き、選択の前提や状況理解が変わったなら、その改善を記録する。少数回の試行を、効果がないという断定や普遍的な改善率へ広げない。

完了報告には、解消した原因、利用者へ新たに届いた内容、異なる設定での確認、維持した制約と検証結果を示す。移動量の改善が未確認なら、そのまま未達として残し、基盤修正やPRのマージだけで元の目的を達成したと扱わない。
