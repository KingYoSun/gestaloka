# ADR-046: 構造化出力と修復入力の情報保持

状態: 採用。2026年11月17日のユーザー判断に基づく実装。費用と提示内容の比較は[評価記録](../evaluations/ember-structured-output-2026-11-17.md)を参照する。

## 原因

#191適用後の本番記録では、Emberへスキーマを本文で送っていたが、API指定はjson_objectだった。項目の階層誤りと、空白を大量に出力して65,536トークンで終了する応答があった。修復で原応答を追記するため、失敗が後続の入力費用も増やした。

## 決定

OpenRouterへ応答スキーマを持つ要求を送る際は、response_formatでjson_schemaとstrictを指定する。モデルIDによる分岐や、本文・選べる行動・出力件数の制限は加えない。

提供先が要求する「最上位はobject」「全項目をrequiredへ列挙」に対応するため、API通信ではresponseへ応答を包む。任意項目は未指定をnull、指定された値を{value: 値}で表す。明示的なnullも{value: null}として未指定と区別し、受信後に既存のアプリ形式へ復元する。query・context・sceneを維持し、意味を省いたスキーマへ切り替えない。既存のZod検証は継続する。

JSON解析・表示・形式修復にはmessage.contentだけを使い、reasoning・reasoning_detailsを混ぜない。OpenRouterではreasoning.excludeで推論本文の返却を抑える。推論量は変更せず、推論トークンを出力使用量の内数として精算する。返却抑制を推論の無課金化とは扱わない。

新しい要求を送る共通の組立てで、assistantのJSON候補の文字列外にある空白・タブ・改行の連続だけを一つの空白へ縮める。引用文字列・エスケープ・ID・数値・項目と候補の順序を保持し、不完全なJSONへ括弧を補わない。原要求・原応答と表示済み履歴は保存し、送信済み要求の再利用では既存の要求・応答を使う。

再試行回数・最大出力・上位への引き継ぎ条件は維持する。通常プレイに内容の検品・改善専用のLLM呼出しを追加しない。

## 完了判定

1. 送信形式とAPI形式からの復元、未指定と明示null、contentとreasoningの分離、原応答・保存済み設定・使用量の保持を単体・結合試験で確認する。
2. 保存済み15処理の同一初回入力と固定した取得資料から旧・新各1回を実行し、追加照会・修復・上位呼出し・未確定予約を含む総費用と上位呼出し数を比較する。
3. 異なる2設定の各2初期状態で旧・新各1回、計8シーンを最大4入力で実行する。あらすじ・全応答・リザルトから、状況理解・人物や関係の解釈・次の選択の前提を変える重要な情報を原文で比較する。特定の台詞・行動・結末の一致や、指示への正確な追従を品質の採否条件にしない。
4. 費用と上位引き継ぎが減り、重要な情報や選択の意味の欠落が見つからなければ採用する。未確定予約で総費用の大小が逆転し得る場合は費用削減の判定を保留する。関連検証と必須CIの通過後にマージし、本番のソース・実行物・healthを照合する。

少数の事例から全世界の品質や削減率を保証しない。数値・比較対象・診断途中の費用と限界は評価記録へ残す。
