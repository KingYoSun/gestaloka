# ADR-041: 所在地の内部操作と共通の現在地

状態: 採用。2026年11月16日。

## 問題

移動の本文が生成されても任意項目の所在データが省略され、一覧には前の所在地が残った。接触判定は別シーンの行動履歴を参照していたため、両者の現在地が食い違った。また、参加先のシーン時計が直前の所在地記録より古くなる場合があった。

## 決定

- 所在地は `locate(subjectId, text, aboutIds)` の型付き操作として扱う。物品・保管先・技能と同じ `planBelongings` / `changeBelongings` を共用し、同じ行動で生じた変更を原子的に確定する。意味上の所在地は自由記述と存在への参照で表し、場所の種類や世界設定を列挙しない。
- 操作は最新の所在地を照会し、旧content/aboutを閉じて新しいstatusを保存する。旧記録より古い時刻で閉じず、記録の終点・始点まで確定時点を引き上げる。同じ所在地なら書き直さない。同じcommitIdの再送と依存版の競合検査は既存の確定処理を使う。
- シーンの新しい行動解決では、各eventのlocationsに行動主体の結果時点の所在地を必須とする。動かなかった場合も現在地を返す。欠落や主体の不一致は表示・確定前に通常の形式修復へ返す。実行側が最後の所在地をlocate操作へ変換するため、モデルはグラフ差分を作らない。
- 開始背景で確定した所在地は既存の所在地があっても表示前に内部操作で更新する。背景追記や参加者の追加では既存人物を移動させず、未記録の所在地と必要な同一性だけを初期登録する。終了時は確定済みの所在地・同一性を重ねて作らず、表示した出来事・受容を従来どおり保存する。既存シーンの本文と履歴は改訂しない。
- 初期登録と通常の行動更新は別の確定IDを使う。確定後・保存前の再開では完了済みの応答を保持し、初期登録の再送が次の行動更新を消費しないようにする。
- 一覧・接触判定・行動解決は共通の `locationRecords` を最新の確定状態に対して使う。参加要請の `positionRelationId` は、対象本人の最新所在地レコードのIDだけを受理する。一般の状態、別の人物、過去の所在地のIDで代用しない。行動解決ごとに所在を読み直し、生成中の移動は依存版の競合として再取得・再解決する。背景や行動履歴は当時の記録として渡し、現在地を復元する代替経路にしない。一覧取得時のモデル呼び出しは追加しない。
- シーンの処理時点は、シーン自身・共有世界・参照する所在地の確定時点より前に戻さない。内部操作で確定時点が進んだ場合は、その行動の出来事の終点も合わせる。既存の出来事の期間は変えず、便宜的な時刻加算で順序を表さない。
- 世界更新の所在地操作も同じ内部処理へ通し、モデルがlocationの関係を直接追加・終了する経路を認めない。操作の選択と場所の意味判断はモデル、型・版・期間・DBの確定は実行側の責務とする。点検用の追加モデル呼び出しは設けない。

## ADR-042による接触契約の統合

[ADR-042](ADR-042-game-progress-and-unified-play.md)は、モデルが`positionRelationId`を証明して配送方法を選ぶ出力を廃止する。所在地の正本、`locate`、最新レコードの共通取得、競合検査と時計の補正は維持する。接触は行為の受容から操作担当へ引き継ぎ、経路が未記録であることを不成立の証拠にしない。

## 互換性と検証

既存のstatus/contentの `text="location"` を引き続き読む。API・Web・CLIの `locations: string[]` は変更しない。保存済みの旧eventのlocations省略は履歴として読めるが、新しい行動解決の応答には許容しない。

実DBで時刻補正・旧所在地の終了・再送・競合、一覧と接触文脈の一致を検証する。下位モデルを使った隔離シーンで、古い時計からの移動、更新後の一覧、旧所在地からの呼びかけ、移動先からの呼びかけを保存入出力と照合する。接触先の返答や協力は成功条件にしない。
