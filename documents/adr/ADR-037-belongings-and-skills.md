# ADR-037: 物品・保管先・技能を表すhasの役割と要約

2026年11月15日採用。2026年11月28日に技能要約の廃止を承認（[#589](https://github.com/KingYoSun/gestaloka/issues/589)）。

## 対象

[#169](https://github.com/KingYoSun/gestaloka/issues/169)のうち、[#170](https://github.com/KingYoSun/gestaloka/issues/170)が扱うグラフ表現と内部関数を定める。人物生成とシーン進行からの利用は#171、本人向けの取得は#172で扱う。HP・能力値・経験値・技能レベルは導入しない。

3ノード・6関係と確定手続きは[ADR-001](ADR-001-world-graph.md)を引き継ぐ。`has` に役割を加える契約変更と、既存世界の引き継ぎ方法は、2026年11月15日にユーザーの承認を得た。

## hasの役割

`has` は「所有・保持」を一つの関係で表していたため、所有者と携行者、保管先を区別できなかった。本番の世界でも `has` は家と少数の持ち物の所有にだけ使われ、所在は自由記述の `status` に書かれていた。そこで `has` に次の役割を加える。

| 役割      | 接続              | 意味                                                                     |
| --------- | ----------------- | ------------------------------------------------------------------------ |
| なし      | 存在 → 存在・記述 | 所有。従来の `has` と同じ意味で、既存の関係をそのまま読む。              |
| `hold`    | 存在 → 存在       | 物品の所在。人物が保持すれば携行、家や倉庫が保持すれば保管。             |
| `use`     | 存在 → 存在       | 保管先を利用できる。                                                     |
| `skill`   | 存在 → 記述       | 技能。記述には、できることとその範囲を書く。                             |
| `summary` | 存在 → 記述       | 実行側が作る物品・保管先の要約への接続。旧技能要約への接続は履歴に残る。 |

物品と保管先は `existence`、技能は `script` で表す。物品・保管先・技能の種類は列挙しない。贈与は所有と所在の変更、貸与は所在だけの変更、預入は保管先への所在の変更で表す。

一つの物品について、終了していない `hold` は同時に一つだけとする。確定処理が同じトランザクションで検査し、二つ目を拒否する。所有には件数の制約を置かない。

根拠は関係の本文に自由記述で残す。初期設定か、成立した出来事の内容を書く。成立した時点は関係の期間、変更前の内容はノードの改訂履歴から読める。関係を終了しても、物品と技能の記述、過去の関係は残る。

数量は持たない。同じ呼称の物品が複数あれば、その個数を数量として扱う。まとめて扱う物は、一つの存在として呼称に書く。

## 要約

人物には、保持している物品と利用できる保管先の要約を一つずつ紐づける。要約は対象の本文とIDを並べた `script` とし、IDは主体と役割から導出する。物品と保管先の関係や対象の本文が変わったときは、同じ確定で要約を作り直す。

保管先の在庫は保管先自身の要約に書く。利用者の要約には保管先への参照を書く。閲覧者ごとの版や閲覧時刻は持たない。

## 技能の参照と枠数

現在の技能一覧は、本人から出る有効な `has(skill)` から取得する。本文が必要なときは、参照先の技能IDで読む。技能の確定記録には、変更した個別技能と関係を記録する。技能枠の使用数は人物に保存し、技能関係の追加と終了の差分を同じトランザクションで反映する。

移行時に旧技能要約への関係を終了し、旧版の枠数を人物に引き継ぐ。旧版に枠数がない場合は、その時点の有効な技能関係を数える。切替前の要約本文、改訂履歴、保存済みの確定記録は当時の内容を参照できる。旧要約IDを本人が現在の対象として検索したときは、本人検索から個別技能を読めることを案内する。

## 内部関数

`changeBelongings` は、対象のIDと型付きの引数を持つ操作の配列を受け取る。操作は、物品の生成、所在の移動、所有者の変更、保管先の利用の開始と終了、技能の習得、本文の改訂、除去の八つとする。グラフの照会と差分の組み立て、変更の前提の確認は関数が行い、呼出し側はクエリや差分を書かない。

移動には現在の保持者を指定する。指定が最新の所在と異なれば拒否する。同じ `commitId` の再送には保存済みの確定記録を返し、再適用しない。新しいノードと関係のIDは `commitId` と操作の位置から導出する。同時に確定した変更は、既存の依存版の照合によって一方だけが成立し、他方は競合として呼出し側へ返る。

`readBelongings` は、主体の保持する物品、利用できる保管先とその在庫、技能を、指定した時点または最新の確定状態で返す。関係を読むだけで、観測や出来事を追加しない。

世界更新の提案には、役割つきの `has` の追加と終了を認めない。物品・技能の事実は内部関数と管理編集だけが書く。

## 既存世界

役割を導入する前の `has` は、所有としてそのまま有効とする。過去の関係を一括で書き換えない。

所在と技能は、既存の自由記述から機械的には決まらない。そのため製品に取り込み処理は実装せず、運用者が管理MCPで確定済みの記述を読み、根拠を示せる事実だけを管理編集で追加登録する。同じ要求IDの再送は同じ確定記録を返す。

## 互換性

既存の保存データはそのまま読める。役割つきの `has` を含む世界のデータは、役割を知らない旧版では検証に失敗する。旧版へ戻す場合は、役割つきの関係を含まない時点のバックアップを使う。

## 検証

実DBテストで次を確認した。物語の内容や結末は期待値にしていない。

- 借りた工具を倉庫へ預けても所有者が変わらず、携行と保管のどちらか一方にだけ現れる。二人の利用者が同じ在庫を読む。
- 倉庫の最後の一品を二人が同時に取り出すと一方だけが成立する。再送と、別のストアからの再開は保存済みの結果を返し、在庫と要約が一致する。
- 技能の習得・範囲変更・除去の前後で、各時点の一覧と根拠、過去の関係を読める。
- 役割導入前の所有を保ったまま事実を追加登録でき、同じ登録を繰り返しても関係と要約が増えない。物品の本文を改訂すると、保持者の要約が同じ確定で追従する。

技能要約の廃止は、旧要約の移行を再実行した場合、旧要約の全文を過去時点から読む場合、長い個別技能を複数持つ人物が技能を発展させる場合を実DBで検証する。発展の確定記録に技能全体の本文が含まれず、再送で保存済みの確定記録を返すことも確かめる。
