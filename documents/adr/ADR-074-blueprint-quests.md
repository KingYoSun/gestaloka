# ADR-074 設計図から建築・開店のクエストを作る

2026年11月21日。[#308](https://github.com/KingYoSun/gestaloka/issues/308) の実装方針。建築完了時に入店と保管を可能にし、開店前に中止しても建屋を残すことをユーザーと確認した。

## テンプレートと設計図

プレイヤーが材料を集めて店を建てたとき、その場にいなかった人も道から店を見つけて入れるようにする。テンプレートの作者が一度組み立てた操作を、二軒目の店主や客が覚え直す必要はない。

初版は建築と開店の二段階を実装する。公開するテンプレートは「建築」「既存の場所で開店」「建築から開店まで」の三つ。最後のテンプレートでは、建築の成果である場所を開店の入力に渡す。建設地、店主、商品、交換条件は各設計図の入力とする。建築用の材料はテンプレートで定め、指定のないテンプレートでは申請時に入力する。

作者は人と開発用モデルの協働で、入力項目、段階ごとの材料と同意、成果とその帰属、利用者への案内を定義する。検証用の世界で別の軽量なbotが作者の介助なしで利用できた版を公開する。途中で作者が補った手順は定義か実装に戻し、再度試す。公開版には発祥の世界と原案者を記録し、初の公開で原案者を一度顕彰する。公開済みの選択肢で表せない希望は、新しい遊び方の提案として残せるようにする。

MCPの `blueprints_create` に、発祥の世界ID、テンプレートの名称と版、原案者の人物ID、案内文、完成後の効果を指定する。建築を含む場合は消費材と道具の呼称と必要数も指定する。返された下書きのIDを、発祥の世界で原案者または `testerIds` に指定した人物が `blueprint-propose` に渡して試す。その設計図の建築条件にはテンプレートに記録した材料を使う。

試遊後は、同じ世界で `blueprints_publish` の `template.templateId` に下書きIDを指定する。その版は公開一覧に出て、ほかの世界でも選べる。同じ内容で作成要求を再送すると同じ下書きIDが返る。案内や材料を改めるときは版番号を上げる。作成と公開に必要なMCPのscopeは、それぞれ `blueprints.create` と `blueprints.publish`。

## 申請と現地での参加

CLIでテンプレートを選ぶと、必要な入力と完成後に誰が何をできるかが分かる。申請時に参照先、権限、同意を確認する。GMは世界・場所・規模・材料の妥当性を着手前に判定し、差し戻すときは理由を返す。採用時にテンプレートの版、入力値、各段階の条件、報酬と帰属を固定する。

新たな生成判定を求めた申請は、探索・生成と共通の日次枠から申請者の1 SPを使う。入力不備など判定前の拒否と同一結果の再利用は0 SP。材料の提供、進捗照会、達成は0 SPとし、材料を新規生成する場合は通常の生成として扱う。GMの応答待ちの間はDBロックを保持しない。

採用したクエストは世界と場所に結び付ける。後から別のセッションで来た人も、現地で完成予定の効果、段階ごとの必要数・提供済み数、自分が次にできる操作を確認できる。現地の一覧は場所から、進捗はクエストと材料の項目から索引で引く。提供のたびに項目の合計を更新し、表示のために全提供履歴を読み直す処理を避ける。

## 本人がいま実行できる操作の確認

`blueprint-show` に、本人の直接の滞在先、提供を受け付ける場所、同意・着工申請・提供・取り下げ・中止の可否を返す `actions` を加える。各操作の可否はクエストの段階と本人の役割で判定し、操作できないときは理由と次にできることを示す。着工申請は同意、現地、本人の通常手番、SP残量も確認する。既存の `next` を利用するCLIと互換性を保ち、現地の一覧から個別の照会へ進める。

開店時は、申請で指定した在庫のIDからそのまま提供の可否を調べる。建材や道具のように呼称で指定された要件は、本人が `blueprint-show` に要件番号と候補の品IDを添えると照会できる。品を指定するまでは、照合に必要な入力を案内する。現在地、所持先、現地の保管先を使う権限を、提供時と同じ基準で照合する。

利用できる品について、所持数、取り置き総数、クエストの残り必要数、今回提供できる最大数を返す。最大数は、所持数から全クエストの取り置きを引いた数と残り必要数のうち小さい方で決める。最後の提供で建築・開店の条件を満たせないときは、その理由と、途中まで提供できる数を示す。例えば、最後の1個で開店するところで店主の保管先登録が外れていれば、提供可能数は0個となり、店主の保管先登録が必要だと分かる。利用権限がない品については、その理由と本人の提供可能数だけを示す。

照会と実行で、品の利用権限、数量、最後の提供を受け付ける条件の判定を共用する。可否の判定はその時点の状態を読むだけで行い、照会の消費SPは0とする。実行時に最新の状態を再確認し、確定時には依存版も照合する。参照はクエスト、本人の現在地、指定された品と保管先、取り置きの索引を起点とする。

| 確認する場面                                               | 完了を判定する方法                                                                                                                                                                   |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 現地の参加者、遠隔から照会する店主、同意前や手番外の発案者 | 同じクエストをそれぞれ照会し、現在地と操作の可否、移動・同意・手番待ちなどの理由が本人に合うことを結合試験で確認する。                                                               |
| 開店用の在庫と、IDを指定した建材                           | 手持ち、現地の自分の保管先、利用権限のない品で表示を比較する。所持5個、取り置き2個、残り必要数4個なら3個を提供でき、4個の提供は拒否されることを実行結果と照合する。                  |
| 開店に必要な最後の在庫と、照会後に状態が変わる場合         | 店主の保管先登録がある場合は最後の提供で開店し、登録が外れた場合は照会で理由を確認できることを試す。照会後に品や現在地が変わった場合は、実行時の再確認で確定が止まることを検証する。 |
| 従来のCLIからの照会                                        | 従来の引数で`blueprint-show`と`blueprint-list`を実行し、既存の進捗項目と`next`を読めることを確認する。                                                                               |

## 材料と段階の確定

提供者は実在する品と数量を選ぶ。消費材、達成後も残る道具、開店時に店へ移す在庫を区別する。取り置きは品と数量に結び付け、通常の移動・消費・公開交換からも同じ利用可能数を参照する。未確定分は本人の取り下げまたは中止で解放する。各成果物から、共通の原案者・発祥と、今回の発案者・店主・協力者をたどれるようにする。

- **建築**では建材を消費し、建屋、建設地と行き来できる経路、店主の保管先登録（役割 `use` の `has`）をまとめて確定する。この時点から第三者が入店でき、店主は保管できる。
- **開店**では指定した店舗への店主の登録・同意を確認し、予約した初期在庫をその店舗へ移して公開交換の条件を有効にする。既存店ではこの段階から始める。建築済みの店で開店を中止したときは、建屋・経路・保管先登録・消費済み建材を確定済みとして扱い、開店用の取り置きを解放する。

数量の分割と消費は `planBelongings`、経路は探索の場所・経路生成、購入は `PlayApplications.exchange` の処理を使う。現行の `offer` は売り手の現在地を使うので、店主が事前に同意した店舗と交換条件を使って公開する部分を切り出す。在庫の分割・合流が起きた場合は、移動後に店舗が実際に持つ品を交換条件に結び付ける。

段階ごとにクエストIDと段階から確定IDを決める。最後の提供が重なったら、残数と段階を再確認し、必要数だけを引き当てる。素材と成果物のグラフ変更は同じ確定に含める。グラフとPostgreSQLの間では、確定前に処理内容を保存し、グラフの確定記録から再開できるようにする。開店の公開交換・段階の更新・通知の配信予定はPostgreSQL側で一緒に確定する。途中停止後も続きから完了させ、宛先ごとに同じ通知IDを用いて、店主や協力者に完成場所を知らせる。

## 実装順と完了判定

1. テンプレートの版、申請・採否、現地での照会をプレイヤー契約・サーバー・CLIに通す。新規生成判定、判定前の拒否、同じ申請の再送について、GMの実行回数とSP残量を確認する。
2. 取り置き、取り下げ、建築を実装する。架空の世界で別セッションの二人が建材を提供し、第三者が道から入店でき、店主が保管できることを結合試験で確認する。取り下げた品の再利用、道具の返却、他の取引との二重利用防止、最後の同時提供、確定途中で停止した後の再送も検証する。消費量、建屋、経路、登録、各宛先の通知を照合する。
3. 開店と二段階の進行を実装する。既存店での開店では元の場所IDと建材が変わらないこと、建築後に中止した場合は店に入れて販売は始まらないことを確認する。開店まで進めた場合は、初来店の客が店主の不在時に購入し、店の在庫・売上と客の持ち物が一致するところまで試す。
4. 検証用の世界で、別の軽量なbotに公開候補のテンプレートと通常のCLIだけを渡して二軒目を開いてもらう。初来店の第三者が利用でき、両店から共通の由来と各店の関係者を確認でき、顕彰が一度だけなら公開する。
