# ADR-075 新しい物品受け渡し用の家具の製作と設置

2026年11月22日の実装方針。[#343](https://github.com/KingYoSun/gestaloka/issues/343) の最優先項目を扱う。**特定のテンプレート専用の実装は厳重禁止。** 名称やID、家具の呼称を条件にした分岐、専用の進行形式・コマンド・プロンプトは設けない。試遊例には広場の棚を使う。

## 実装済みの前提：固定場所の保護

場所・人物・物品はいずれも共有グラフの `existence` である。以前は、店主が建屋の所在を変更でき、元の道との接続が残る場合があった。固定場所の保護は本番適用済みで、ぶー村821件・運用検証用世界3件を確認した。家具の設置・移設にはこの保護を使う。固定の印が付いていないことだけでは、移設する権限は得られない。[PR #344](https://github.com/KingYoSun/gestaloka/pull/344)

### 既存世界で確認できた識別根拠

2026年11月22日、本番のぶー村と運用検証用世界を読み取り専用で調べた。経路の端点は、存続中の `status/content` に `route` が付き、同じ `script` から `status/about` が各端点へ戻る関係で識別した。二つ以上の異なる `existence` を結び、両向きで端点の集合が一致するものを数えた。人物の現在の直接滞在先は、操作対象の人物と登録NPCについて、`directPlaces` と同じ最新の所在記録と `direct-place` の条件で集計した。いずれも重複を除いた存在数である。

| 確認項目                                                  |    ぶー村 | 運用検証用世界 |
| --------------------------------------------------------- | --------: | -------------: |
| `existence` の総数                                        |     3,091 |             22 |
| 有効な経路の端点                                          |       791 |              0 |
| 端点のうち、操作対象の人物または現在誰かが持つ物          |         0 |              0 |
| 人物の現在の直接滞在先（うち経路の端点にないもの）        |  35（13） |         2（2） |
| 人物の過去を含む直接滞在先（うち経路の端点にないもの）    | 794（16） |         2（2） |
| 現在の保管先登録 `use` の対象（うち経路の端点にないもの） |   28（1） |         0（0） |

ぶー村の有効な経路記述784件はすべて端点の参照が双方向で一致した。一方、経路の端点に含まれない保管先には、居住に使われている記録がある。経路の端点に含まれない過去の直接滞在先16件のうち1件は、現在、役割なしの `has` で所持されている。初期の `rootIds` にも人物が含まれる。したがって、経路は自動識別に使えるが、経路だけで全ての場所を拾うことはできず、滞在先・保管先・生成時の起点を一律に固定すると人物や物品を巻き込む。地名らしい文字列や所在の補助的な `aboutIds` は、単独の判定根拠にしない。[経路の意味](ADR-063-routes-in-surroundings.md)と[所在の読取](../../packages/server/src/world/locations.ts)を参照。

### 保護対象の確定

- 既存世界では、一度の移行で有効な経路の端点を抽出し、人物や現在の所持品と重ならない端点を固定場所として記録する。重なるものや不完全な経路は個別確認に回す。経路のない滞在先、保管先登録だけがある家、終了済みの経路、古い所在の補助参照などは候補として提示し、管理者が世界内の記録を確認したものを追加する。**滞在履歴だけでは固定しない**。未確認の候補には制限を適用しない。
- 判定結果は世界と存在IDで直接引ける、サーバー管理の「固定場所」の印として共有グラフに保持する。既存のID、関係、過去の所在を維持する。道の廃止、所有や保管先登録の変更、人物の入退室でこの印は消えない。新しく探索・建築・世界生成・参加処理で固定の場所を成立させるときは、その場所を作る確定で印も付ける。通常プレイからの自由記述や任意の参照を根拠に、他人や物品に印を付けたり外したりできないようにする。
- 移行前に世界ごとの自動判定数、個別確認件数、人物・所持品との重なりを提示する。上の数値は調査時の2世界の結果であり、他の世界を同じ割合で分類できるという前提は置かない。通常プレイ時の判定では、操作対象のIDだけを照合する。

### 操作のどのIDを検査するか

固定の印は共有グラフの `WorldNode.fixedPlace` に保存する。プレイヤーが送るノードや操作の入力には含めない。探索と建築では新しく作った場所、初期生成と参加処理では承認された提案中の新規の固定場所に印を付ける。既存の場所は世界ごとに次のコマンドで集計する。

```sh
node --import tsx scripts/protect-fixed-places.ts --world <構築世界ID> --decisions <判定JSON>
```

判定JSONには対象の `world` と、確認した存在IDの配列 `fixed`・`movable` を指定する。既存世界の記録を含む判定ファイルは非追跡領域に保管する。コマンドは既定で件数を返し、`--apply` を付けると固定の印を保存する。確認済みの44件と2世界の経路・所持・操作対象の構造を使った隔離試験では、ぶー村相当で821件（経路791件・個別30件）、運用検証用世界相当で3件を固定した。移動可の11件はすべて保護対象から外れ、再適用で追加された印は0件だった。

| プレイヤーの操作      | 固定場所の印を照合する対象 | 期待する動作                                                                                                                                  |
| --------------------- | -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 所在を変える `locate` | 動かす主体 `subjectId`     | 店自体を別の場所へ移す申請は店主でも拒否する。人物が店に入る申請では人物が主体であり、行き先の店はこの制限に掛からない。                      |
| 所持先を変える `move` | 運ぶ品 `item`              | 店自体を持つ・渡す申請は拒否する。店から椅子を運び出す申請では椅子を照合し、`from` や `to` の店には従来の保管先・現地・受領の条件を適用する。 |

プレイヤー起点の申請で共通の判定を使う。単独・複合の申請、対抗行動、受領後の確定、グラフ差分で同じ移動を表す経路にも適用する。操作対象と、単に参照する場所を区別し、移動の成否をダイスやLLMに委ねない。確定時にも保護対象の版を照合する。複合申請に禁止された移動が含まれる場合は部分適用しない。管理修正は既存の明示的な権限と監査を通す。

隔離試験では、店主本人でも建屋の所在・所持先を変更できず、入退店と物品の出し入れが成功することを確認した。過去に滞在先として参照された移動可能な品、複合申請、受領待ちの間に固定された場所も検証した。

## テンプレートの定義とプレイヤーの入力

| 誰がいつ決めるか         | このテンプレートでの内容                                                                                                                                                                                                                                                                                                                         |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 作者が版に固定する       | 名称「新しい物品受け渡し用の家具の製作と設置」、版、原案者、案内文、進行形式 `craft`、製作に使う材料・個数・消費の有無。完成時に空の保管先を現地に設置して管理者に登録し、現地での無償の受け渡しと管理者による移設を利用できるようにする。受け渡しの対象は「現地の誰でも」「指定した本人」の両方を許す。材料の呼称と数量は下書き作成時に定める。 |
| 発案者が設置を申請する   | 今回の設置場所、家具の名前、管理者を指定する。参加者が実物の材料と道具を提供し、空の家具を使えるようになれば設置クエストは完了する。                                                                                                                                                                                                             |
| 管理者が品を預ける       | 現地で品を家具へ移し、その実物から、公開する個数と相手を指定して取り置く個数を決める。受取人は現地で自分が使える枠と個数を選ぶ。同じ家具を何度でも使える。                                                                                                                                                                                       |
| 管理者が完成後に移設する | 家具と移設先を指定する。家具ID、中身、掲示、指定相手と残数、過去の受領履歴は引き継ぐ。                                                                                                                                                                                                                                                           |

物品を製作する進行形式には `craft` を使う。既存の `build` は入店できる建屋を作り、経路を結び、固定場所として登録する。`craft` は材料と道具が揃うと新しい物品の `existence` を一度だけ確定する。材料の提供・取り置き・消費、道具の解放、競合・再送時の確定処理は共用する。受け渡し用の家具では、製作した物品に「現地への設置と保管先登録」「無償の受け渡し」「管理者による移設」を定義で組み合わせる。これらは `craft` を選んだ全物品には付与しない。

## 追加する共通機能

テンプレートの作成・公開、管理者の同意、着工時のGM審査、材料と道具の提供、クエスト達成の確定には既存処理を使う。空の保管先が設置された時点でクエストは完了する。その後の受け渡しと移設は、完成時に確定した保管先IDと利用条件から実行する。

| 実装順 | 共通機能                                           | 現行との差と実装範囲                                                                                                                                                                                                                                                                                                                                               |
| ------ | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1      | 物品製作用の進行形式を追加する                     | テンプレート契約・設計図の申請・CLIに `craft` を加え、一覧には製作する物品とその利用条件から効果を表示する。製作する物品、設置の有無、完成後に許す操作を採用時に固定する。建屋用の経路生成や固定場所登録は `build` に残す。                                                                                                                                        |
| 2      | 設置した保管先を発見・移設できるようにする         | 家具は設置先に所在する一つの `existence` とし、管理者の保管先登録（`has/use`）と結ぶ。既存の建屋は道で結ばれた固定場所、家具は現地から操作できる保管先として設置する。移設では、定義が移設を許すこと・操作する人が管理者であること・対象が固定場所でないことを照合する。通常の `move` や `locate` を含め、設置済みの保管先の所在を変える経路に同じ条件を適用する。 |
| 3      | 保管先の品に受領条件と数量を掲示する               | 掲示には保管先ID、預けた人、実物の品ID、誰が何個受け取れるかを保存する。管理者が品を預け、公開分と指定分の合計を既存の取り置きで確保する。部分受領では選んだ枠の残数と予約数量を一緒に減らし、取り下げでは未受領分を解放する。現在の公開交換は掲示時の場所で検索するため、移設できる保管先の掲示はその現在地を使って引く。                                         |
| 4      | 現地で受領を確定し、当事者が履歴を読めるようにする | 現在の公開交換は支払い品を必須とする。品の照合・分割・移動・確定後の通知を再利用し、定義で選んだ対価の条件と掲示の受領対象を判定する。この家具は無償、商店の従来の公開交換は有償である。受領記録を一件の確定に結び付け、当事者だけに返す。                                                                                                                         |

物品やテンプレートの呼称は表示と材料の指定に使う。たとえば、移設できる保管先だけが必要な別のテンプレートでは、設置と移設を選び、受領枠の掲示は選ばずに済む。家具用のモードや専用コマンドを増やす代わりに、この組み合わせを共通の契約とサーバー処理で扱う。

## 確定と互換性

- **受領**では、管理者の在席を必要としない。サーバーは受取人と保管先の現在地、掲示の受領対象、品の所在、残数を照合する。指定枠は第三者への応答から除く。品の移動と取り置きの減少を同じグラフ確定に含め、残数・履歴・当事者への通知の配信予定も同じ確定IDに保存する。途中停止や再送では、その確定記録から通知と応答を復旧する。
- **移設**では、旧所在地の終了と新所在地の記録を一度に確定する。掲示と履歴は保管先IDに結び付け、現地の一覧は現在の所在から引く。移設後は新所在地で受け渡しを再開する。旧所在地で取得した掲示からの受領も、確定時に現在地を照合して拒否する。
- **照会と費用**では、現地の掲示は場所・保管先、指定枠は受取人、履歴は当事者・保管先の索引からページ単位で取得する。設置時の新規GM審査は1 SP、掲示・受け取り・照会は0 SPとする。

既存契約は [ADR-069](ADR-069-deferred-receipts-and-exchanges.md)、[ADR-072](ADR-072-possession-and-storage.md)、[ADR-074](ADR-074-blueprint-quests.md) に従う。実装時は [テンプレートの型](../../packages/contracts/src/play.ts)、[クエストの確定](../../packages/server/src/runtime/blueprints.ts)、[時間差受領と公開交換](../../packages/server/src/runtime/play-applications.ts)、[取り置きの確定](../../packages/server/src/world/store.ts) を起点にする。

## 受入条件と判定

以下では、広場に設置する棚を試遊例とする。

共通機能の判定には、名称・材料が異なる二つの架空の定義を使う。同じ受け渡し条件を選んだ両方で、同じCLI操作から無償受領と宛先照合が働くことを確認する。片方だけ移設を許し、その差も定義に従うことを確かめる。差分レビューでは、名称・IDによる分岐や家具専用の操作がないことを確認する。互換性試験には、完成時の操作を指定する項目がない既存の保存版を使う。

| 対象               | 隔離環境で確認する結果                                                                                                                                                                                                                                          |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 棚の設置           | 検証用のテンプレートを選び、建材を提供して広場で棚を使える。棚は設置者の登録済み保管先になり、広場で従来の出し入れもできる。                                                                                                                                    |
| 公開分と指定分     | 一つの品を3個置き、公開2個とBさん宛て1個を掲示する。預けたAさんは別の場所へ移動して退出する。Cさんは広場で公開分を1個受け取り、Bさんは同じ広場で指定分を受け取る。棚に公開分1個が残り、受取人の手元へ各1個が移る。                                              |
| 権限               | Cさんの一覧にはBさん宛ての枠が出ず、枠を指定しても受け取れない。通常の移動で取り置き分を取り出せず、離れた場所からの受け取りは拒否される。                                                                                                                      |
| 同時受領と再送     | 残り1個に対して受け取りが重なった場合、成功は1件となる。同じ要求を再送しても、物品、残数、受領記録、通知は一度だけ更新される。                                                                                                                                  |
| 取り下げ           | 預けた本人が掲示を取り下げると、未受領分を通常の移動で使える。                                                                                                                                                                                                  |
| 受領履歴           | 受取人、個数、時刻が確定時の記録と一致し、預けた本人と受け取った本人が確認できる。無関係の来訪者からは履歴を読めない。                                                                                                                                          |
| 既存の公開交換     | 従来のCLIで公開交換を一覧から選び、商品と代価を従来の形式でやり取りできる。                                                                                                                                                                                     |
| 完成後の移設       | 設置クエスト達成後、管理者が棚に3個置き、公開2個・Bさん宛て1個を掲示する。Cさんが広場で公開分を1個受け取った後、管理者が棚を自宅前へ移す。移設前後で家具IDと中の品を照合し、残りが公開1個・Bさん宛て1個であることを確認する。管理者以外による移設は拒否される。 |
| 移設先での受け渡し | 広場の一覧から棚が消え、旧掲示を指定しても広場では受け取れない。自宅前ではCさんが公開分、Bさんが本人宛ての分を各1個受け取り、棚の残数は0になる。広場での最初の受領記録も、移設後に当事者が同じ棚の履歴から確認できる。                                          |

## 隔離環境での試遊（2026年11月22日）

専用のPostgreSQLとNeo4jに架空の世界と3人のプレイヤーを用意した。材料と受け渡す品は開始時に配布した。使った定義は[新しい物品受け渡し用の家具の製作と設置](../../examples/blueprints/item-handoff-storage.json)。

| 場面             | 観測した結果                                                                                                                                                                                                                              |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 下書きと製作     | 運営用MCPで下書きを作成し、一台を試作して同じ版をID指定で公開した。軽量botはプレイヤーCLIで公開一覧から選び、自分が管理する二台目を申請した。木板2枚と組立用の木槌1本を提供すると製作クエストが完了した。木板は消費し、木槌は手元に残る。 |
| 不在時の受け渡し | 軽量botは焼き菓子3個を家具に入れ、公開2個と知人宛て1個を掲示した。ここで管理者のセッションを終了した。別の来訪者には公開枠だけが見え、そこから1個を無償で受け取れた。                                                                     |
| 移設             | 管理者が戻って家具を移すと、旧設置先での受領は拒否された。新設置先では同じ家具IDに公開1個と知人宛て1個が残っていた。来訪者と指定された知人がそれぞれ受け取ると残数は0になり、管理者の履歴には移設前の分を含む3件が残った。                |

軽量botが操作を選んだのは、所持品の確認から掲示までの8手。以降の退出・受領・移設は試験からプレイヤー操作を実行した。試作を含む2件の製作審査は各1 SPで、GMの実測費用は2回で計0.006288米ドル。軽量botの操作選択は8回で計0.028620米ドルだった。

同じCLIを使う統合試験では、材料を石材に変えた受領台を製作した。定義の `relocatable` を `false` にすると、公開・宛先指定の受け渡しはでき、管理者の移設申請は拒否された。`installation` を省いた布製品は製作者の所持品になった。また、公開枠の最後の1個を2人が同時に要求しても成功は1人だけだった。受領確定直後の通知中断と同じ要求の再送を挟んでも、受領3件に対して履歴は3件、通知は預けた人と受け取った人に各1通の計6通だった。[統合試験](../../tests/integration/bot-play.test.ts)
