# 派生グラフを残し、events側の重複を省くローカル検証

派生グラフを全量残したまま、eventsから重複する本文・行為者・期間を省く案を実装した。保存済みの4シーンを各条件1回ずつ、共有世界への確定からリザルト生成まで実モデルで比較した。終了処理の初回入力は4.15%、リザルトを含む総入力は2.69%減った。呼出し数は減っていない。

今回の4組では、リザルトへ渡る確定情報と実際のモデル入力が各組で同一になった。全提示を読んだ比較でも、リザルトによる物語移動量の差は観測しなかった。一方、実測費用の6.00%減はキャッシュと生成量の差を含む。キャッシュを使わない単価へ揃えると0.41%減に留まり、安定した費用削減率として6%を見込む根拠にはならない。

変更と検証はローカルのみ。本番への接続・write・デプロイは行っていない。

## 対象と完了範囲

- #191適用後の保存済み本番19操作について、eventsを元通りに復元できるか、入力ID・所在地・受容情報が残るかを照合する。本番の再取得はしない。
- 保存済みの2設定・4シーンを、全量供給とevents縮減で比較する。各条件1回、予算上限$8。他の初期供給の限定・派生グラフ省略・待機引継ぎは組み合わせない。
- 元の初期文脈をローカルDBへ復元し、通常のWorldAgentで検証・原子的確定を行う。その後、通常のresultSourceで組み立てた入力を実モデルへ渡してリザルトを生成する。提案JSONだけの比較では終えない。
- 入力トークン・出力トークン・費用・呼出し数と、先行提示からリザルトまでの意味の変化を比較する。通常プレイへ検品用の呼出しを追加しない。

19操作の本番保存資料と、実モデルの4比較に使った資料は区別した。後者は、以前にローカルで生成して保存した「潮の記録庫」2例、「軌道温室」2例である。本番19操作のリザルト品質を再生成して評価したという意味ではない。

## 実装と保持した情報

モデル入力の組立時だけ、completedScene.eventsを次の形にする。

```json
{
  "id": "出来事ID",
  "inputId": "対応する入力ID",
  "locations": ["その出来事の所在地"],
  "receipts": [
    {
      "observerId": "受容者ID",
      "at": "記録にある場合の明示時刻",
      "information": ["出典・evidenceを含む元の情報"]
    }
  ]
}
```

省いた本文と期間は同じIDのanchors.nodesのevent、行為者はそのeventへ入るhappen、受容本文はobserverIdからeventへ向かうseeに残る。eventsの順序、入力ID、所在地、受容者、明示時刻、informationとそのevidenceは保持する。background・sources・intentions・initialContext・派生グラフは削らない。読み先の説明をscene-worldプロンプトへ加え、比較両群で同じプロンプトを使った。

world_operation.requestとシーン保存データは従来の全量のまま。DB確定も元のanchorsを使う。既に保存されたモデル対話を途中で書き換えず、新しく組み立てる終了処理の入力にだけ適用する。

本番19操作の638出来事と、比較用4シーンの30出来事は、残した情報とanchorsから元のeventsに完全に戻った。本番19操作中7操作はeventsが空であり、この方式によるevents削減はない。本番資料のevents単体のJSONは1,192,791文字から868,247文字へ27.21%減ったが、これはモデル入力トークンの削減率ではない。

実際の送信前には既存のrecords/$refによる重複排除が働く。そのため、raw JSONの本文を削った割合ほど、送信トークンは減らない。今回、実送信を展開して照合した22要求すべてで、保持する情報に欠落はなかった。

## 実行条件とローカル復元の制約

実行IDは`43f75f19-8490-43f1-81ce-c6db42657087`。終了処理はGPT-6.1 Terra / Responses / medium、リザルトはMuse Ember / OpenRouter / low、出力上限はいずれも65,536。実行時にモデルAPIで利用可能なIDを確認した。両群の保存済み履歴、スキーマ、モデル設定は共通で、実行順は組ごとに交互にした。温度・seedによる出力固定はしていない。

専用Postgresは127.0.0.1:28533、Neo4jは127.0.0.1:30687。接続先をスクリプト内で固定した。外部HTTPはモデル一覧・生成・入力トークン計測のAPIだけを許可した。8個の独立したローカル世界で、初期文脈と人間操作主体IDが元の保存入力と一致することを、課金呼出しの前に確認した。

復元したのは保存入力に存在する現在の部分グラフであり、当時のDB全体や過去の全版ではない。追加照会は保存済みの取得結果から供給した。ケース2では、保存記録の「場所ノードの状態取得」と同じ状態を「status関係の照会」で求めたため、一度停止した。記録内のcurrentStatesに含まれるscriptと接続を両群へ同じように補い、同一操作を再開した。続くscript取得は保存された本文だけを返し、未取得の追加履歴は供給していないと明示した。未取得を空集合に置き換えていない。

停止前のモデル応答は台帳から再利用し、成功した出力を選び直していない。停止・再開と全課金は記録に残した。このケースは完全なDB復元を使った比較とは扱わず、費用を除外した集計も下に示す。最終的に8件ともローカルの確定レシートと新しいリザルトを得た。

## リザルトの物語移動量

narrative-inspection-v13 / meaning-v6を用いて手作業で評価した。先行提示34件、入力16件、新規リザルト8件を全件読み、リザルト65文の命題を以前の提示へ照合した。入力ごとの目的・実際の応答・変わった判断材料と、全文・提示ID・引用対応はJSONに保存した。

比較窓より前の全履歴とmanifest.initialを揃えたmanifestはないため、全履歴を基準にしたシーン全体の絶対的な新情報総数はnullとする。ただし両群の先行提示は同一であり、リザルトがそこへ何を加えたかという差は比較できる。単に要約が長い、内部statusが多い、待機主体が少ないことは加点しない。

リザルトの0は、シーンが動かなかったという意味ではない。進行中に得た上記の情報を、両群のリザルトが再掲したという結果である。新しい意味単位がないため、リザルトの新規単位の平均重要度は両群ともnull。今回の変更による、この提示窓全体の新情報量の差は0だった。

ケース0では、提示`23668709-be67-4239-a24a-d52e6c294982`に既に「変更後の予定時刻と実際に閉じた時刻がどちらも未確認として残され」とある。全量の「変更後の予定時刻と実際に閉じた時刻は、どちらも未確認として分けて残されています」と、縮減の同内容は新情報に数えない。また、提示`7581fe0d-4deb-4045-a2f9-c5c1a7e883a4`の「滲みが連絡のときについたかどうかは、私にも確かめられません」に対し、両リザルトとも係にも確かめられないと記す。滲みの発生時期について、不明を解決したとは読まない。

ケース1では、提示`32e1852e-6bae-4cc2-afbc-6a9734ca7771`の「まず私が端末で校正値の履歴を確認し、次に栽培槽の葉の巻き具合を観察します」「ご一緒になるかはお任せします」が、今後の予想と選択を変えている。全量は「候補は残したまま今回は一区切り」、縮減は「これらは提案・意向の段階であり、実行や合意として成立したものではありません」とまとめた。これは直前の今後の調査を受ける文として読めるが、「これら」の範囲は読みづらい。以前に行った端末表示の確認まで未実施とする読み方は、元の提示に沿わない。

ケース2の提示`097bd1f5-efe5-40cc-a071-738f058d1840`では「校正の完了を待たずに、巻きの範囲を確かめられます」と提案の理由が届いている。最後の提示`b555f8b9-8250-4c07-a0b8-85480b68593a`には「その提案への同意や確認の実行はまだ選ばれておらず」とある。両リザルトも「その提案への同意や確認の実行はまだ選ばれておらず」を維持した。未選択と分かっていることを、実施したか分からない状態へ弱めたとは判定しない。

ケース3では、提示`88ada999-0a87-47b5-a71e-76d1c03d5b41`で「リツはその連絡が伝言板に残っていることを確かめた」が既に届いている。縮減リザルトは「伝言板に変更後の時刻の連絡が残っていることを確かめました」と詳しく残すが、新しい発見ではない。全量でこの文を省いても、以前に得た知識を否定・不明へ変更したことにはしない。最後の提示`2222d045-60ca-4fba-ac82-18cd1ace5242`で未実施と明示された読み合わせ・元の時刻の読み取り・水門側との照合も、両リザルトで未実施のまま残る。

4組とも、通常のresultSourceで得たconfirmed、その後のsystem/userメッセージ、さらにプロバイダへ実送信したリザルト入力が完全に同一だった。この一致は品質点ではなく、差がどこまで伝わったかを調べる因果追跡である。リザルト本文の長さや記述の細かさの違いは、同じ入力からの生成差として説明でき、終了入力の縮減が違う情報をリザルトへ渡した結果ではない。

## 判断と検証

この案は、派生グラフを省く案よりも、失われる情報を具体的に限定しやすい。今回の資料では入力ID・所在地・受容情報を残し、リザルトの物語移動量の低下も観測しなかった。ただし得られたのは小幅な入力削減であり、呼出し数の削減と安定した総費用削減は確認していない。後続処遇が変わる例もあるため、今回の結果を長期の品質同等性や本番導入の根拠とはしない。ローカルの候補実装として残し、本番には適用していない。

単体102件、agent/scene結合46件、build、typecheck、対象ファイルのESLint、生成契約チェックを通過した。結合テストは、モデル入力が縮減されても保存されたrequestとシーン履歴が全量のままで、終了・再開・競合後も通常の確定へ進むことを検証している。

成果物は同名JSONと、`artifacts/evaluations/event-metadata-2026-11-17/`配下のprepare/run/summarize/qualityスクリプト、固定fixture、実送受信記録、確定レシート、停止と再開の記録。従来の作用経路限定のローカル差分は同ディレクトリの`isolated-effect-scope-prototype.patch`へ退避し、今回の比較へ混ぜていない。
