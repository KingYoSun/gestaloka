# 生成GMで習得済みの技能をキャッシュから読む

OpenAI Responsesで生成判定の技能をキャッシュするとき、成立順の4件目、12件目、28件目と最後の行の後ろに区切りを置くようにした。各ブロックのテキストをつなぐと、変更前の入力本文と一致する。技能の本文、習得経緯、ID、成立順を保ち、申請本文、対象の状態、持ち物などは区切りの後ろに置く。既存の要求IDと保存した元入力を再送の照合に使う。

比較の基準は、消費候補と遠隔保管庫の圧縮を含む `7d6549e0`。本番ログは読み取り、隔離環境の実GMとDBには架空の技能・申請を使った。[保管庫の圧縮の試算](creation-dice-storage-2026-11-23.md)

## キャッシュの区切りを固定した理由

11月22日のぶー村では、アカウントAの技能が変わった33回はすべて末尾への追加で、直前の呼出しから30分以内だった。この33回で旧版のキャッシュ読取は0だった。旧版は技能一覧の末尾に1箇所だけ区切りを置くため、新しい技能が増えると同じ位置に区切りが残らない。

4技能ごとに区切って古い区切りを入れ替えた試作では、同じ技能を渡しても、取り除いた区切り以降のキャッシュを再利用できない例があった。固定した位置の区切りを残すと、技能が増えた場合も、そこまでの内容が同じ区切りを使える。技能の一覧が同じときは、末尾まで読み取れる。技能の本文を改めた場合は、変更した箇所以降を改めて処理する。

## 実GMの使用量と隔離環境での試遊

架空の技能を順に習得して製作する申請を、変更前と変更後のフォーマッタに通して `gpt-6.1-terra` で比較した。APIの使用量でキャッシュ読取と書込を確認し、当時の単価で入力の計算原価を求めた。最後の技能を改める例でも、同じ内容の区切りまでは読み取れた。

| 変更のあった技能     | キャッシュ読取 前 → 後 | 30分書込 前 → 後 | 入力の計算原価 前 → 後（ドル） |
| -------------------- | ---------------------: | ---------------: | -----------------------------: |
| 4件から5件に増加     |              0 → 2,313 |      2,495 → 183 |            0.006044 → 0.003269 |
| 12件から13件に増加   |              0 → 3,444 |      3,596 → 155 |            0.007420 → 0.003291 |
| 28件から29件に増加   |              0 → 6,213 |      6,400 → 192 |            0.010925 → 0.003476 |
| 29件のうち末尾を編集 |              0 → 6,213 |      6,420 → 212 |            0.010950 → 0.003501 |

4件から5件に増える例は、4件の時点ですでに技能のキャッシュ条件を満たす長さにした。技能が同じ29件の繰り返しでは、両版が末尾までを読み、書込は0だった。判定指示が変わる申請では両版とも読取が0になった。旧形式で使ったキャッシュへ新形式で初めてアクセスした試作では、読取が0だった。形が同じ入力が再び届いたときは読み取れた。

製作の実GM応答では、28回すべてで手持ちの麻布2個を消費候補に選んだ。技能発展の例では、変更前後とも在庫にない材料名を返したため、この試行はGMの応答までを確認した。製作の成功上限とファンブルの内容には試行間のばらつきがあった。

PostgreSQLとNeo4jを使う隔離DBでは、技能を16件から17件に増やした後も、既習得分のID、本文、習得経緯、時点、順序が判定に届いた。追加した技能の根拠も次の製作判定に届いた。模擬応答で2回の製作を適用すると、麻布9個から2個、続いて1個が減った。同じ要求を再送した場合は保存結果を返し、消費は重ならなかった。

技能を28件から29件に増やした実GM試行の2応答も、同じ関連技能と在庫を持つ架空の世界で適用した。両版で出目2を使うと、麻布9個から2個を消費して当て布が1点成立し、裁断鋏は残った。再送では保存結果を返した。
