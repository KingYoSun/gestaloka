# 設計図テンプレートを作る

**特定のテンプレート専用の実装は厳重禁止。** テンプレートごとの違いは定義データで表す。名称やIDで処理を切り替える分岐や、一つのテンプレートだけを動かす専用のコマンド・進行形式・プロンプトを追加してはならない。既存の機能で表せない場合は、複数のテンプレートで再利用できる操作や条件として設計する。

## 遊び方から定義を決める

元の遊び方を「何を持って、どこから始めるか」「誰が何を揃えるか」「完成した後、他のプレイヤーが何をできるか」で書き出す。開始条件と成果が名前から読み取れるようにする。たとえば空き地に建材を持ち寄った事例を再現するなら、最初の入力は建設地で、店は途中で誕生する。完成済みの店舗記録で営業だけ試した結果は、その建築過程の検証には使えない。

製作記録を参照する依頼では、記録から材料・道具・協力者の役割・完成時の設備を読み取り、どの要件や操作で再現するかを決める。隔離世界は製作前の状態から始め、成果物がクエストの達成で初めて生成されたことを確認する。原記録に数量や価格がない場合は、試遊で補った値として記録する。案内文を読んで行う作業と、サーバーが達成条件として検証する作業も区別する。

作者が作る**テンプレート**には、名称、版、原案者、案内文、進行形式（`mode`）を持たせる。プレイヤーはその版を選び、今回の場所・店主・商品・交換条件を埋めて**個別の設計図**を申請する。採用後の `phase` はそのクエストが今どの段階にいるかを示す。

| 選ぶ進行形式     | 開始条件                                               | 試遊で確かめる成果                                                                            |
| ---------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| `build`          | 接続元の場所を選び、建材・道具を揃える                 | 第三者が道から入れる。指定した人物が建屋を保管先として使える。                                |
| `open`           | 店主が登録済みの保管先に行き、既存の品と交換条件を選ぶ | 同じ場所で営業を始め、店主の不在時にも客が購入できる。                                        |
| `build-and-open` | 建設地を選び、建築と開店を一件として申請する           | 建材が揃うと建屋が使え、続いて在庫が揃うと営業が始まる。                                      |
| `craft`          | 製作場所・管理者・物品名を決め、材料と道具を提供する   | 一つの物品を製作する。`installation` を指定すると保管先となり、移設の可否と受領対象を選べる。 |

同じ `mode` で複数のテンプレートを作れる。`craft` の設置と利用条件は `installation` で定める。`relocatable` は管理者が移設できるか、`pickup` は許可する受領対象（`public`・`addressed`）を指定する。[家具の定義例](../../../examples/blueprints/item-handoff-storage.json)に発祥の世界の `authorId` を加えて下書きを作れる。希望する遊び方を現行の契約で表せないときは、不足する処理を具体的に示し、機能の設計判断に戻す。現行の定義は [契約](../../../packages/contracts/src/play.ts) と [実行処理](../../../packages/server/src/runtime/blueprints.ts) で確認する。

## 隔離環境で下書きを作る

接続先と `worldId` を確認する。`authorId` は発祥の世界で実際に遊び方を提案した人物のIDを使う。原案者と設置者・店主が同一とは限らないので、原案者が資料から確定しない場合は本人に確認する。下書きで別の人物に試してもらう場合は、その世界で操作できる人物のIDを `testerIds` に含める。

MCPの `blueprints_create` に `requestId`、`worldId`、`reason`、`template` を渡す。次は「空き地に茶店を建てて開く」という架空の例。UUIDは呼び出す環境の値に置き換える。

```json
{
  "requestId": "11111111-1111-4111-a111-111111111111",
  "worldId": "22222222-2222-4222-a222-222222222222",
  "reason": "茶店を建てて営業を始めるまでを隔離環境で試す",
  "template": {
    "name": "空き地に茶店を建てて開く",
    "version": 1,
    "authorId": "33333333-3333-4333-a333-333333333333",
    "mode": "build-and-open",
    "instructions": "建設地で屋台の組立材と木槌を揃える。建屋が完成したら、今回売る品を提供して営業を始める。",
    "materials": [
      { "label": "屋台の組立材", "count": 1, "usage": "consume" },
      { "label": "木槌", "count": 1, "usage": "tool" }
    ]
  }
}
```

`craft`、`build`、`build-and-open` の下書きには `materials` が1件以上必要。`consume` は消費材、`tool` は完成後も残る道具。`open` では `materials` キーを省く。販売する実物のID・初期在庫数・価格は、開店者が申請時に `plan.shop.stock` に指定する。

作成結果の `id`、`state`、原案者・発祥、定義を控える。同じ操作の通信再送には同じ `requestId` を使う。検証中に案内や材料を改める場合は版を上げ、改めた版で試す。

## 作者の助けなしで再現できるか試す

1. 隔離した世界に建設地・必要な品・操作する人物を用意する。原案者または指定した試遊者が下書きIDを `blueprint-propose` の `plan.templateId` に渡し、最初の一件を通す。`blueprint-show` で同意と次の操作を確認し、発案者が `blueprint-start` で着工を申請する。
2. 各段階で、本人が使える品を `blueprint-provide` で提供する。建築を含むなら消費材と道具の行方、開店を含むなら店主が退出した後の第三者の購入と在庫・売上・客の手持ちを照合する。既存の場所を使う場合は、場所のIDと建材も前後で照合する。
3. 隔離環境内でその下書きIDを公開し、別の軽量botに遊びの目標と通常のプレイヤー向けガイドを渡す。botが `blueprint-templates` の一覧から同じ版を選び、具体値を埋め、案内だけで二件目を完了し、事情を知らない別の人物が成果物を使えることを確かめる。作者が途中で操作を補ったら、詰まった箇所を直して再試遊する。

試遊結果には対象の版・進行形式、実際に選んだ操作、確認できた成果と限界を記す。隔離環境の公開と本番公開は別の結果として記録する。プレイヤー操作の入力例と過去の検証条件は [CLI操作ガイド](../../../packages/player-cli/skills/gestaloka-player/references/commands.md) と [試遊レポート](../../../documents/evaluations/blueprint-playtest-2026-11-21.md) にある。

## 依頼された世界で公開し、一覧を照合する

本番公開の依頼がある場合は、対象世界、原案者、名称、版、進行形式、案内文、材料を検証済みの定義と照合する。本番側に下書きがあればそのIDを使う。別の隔離DBで作成した場合は、本番の世界・人物IDで同じ定義を `blueprints_create` に渡し、本番で返ったIDを使う。

`blueprints_publish` の入力は `requestId`、`worldId`、`reason`、`template: { "templateId": "公開する下書きのID" }`。作成と公開は別の要求IDを使う。必要なMCPスコープはそれぞれ `blueprints.create` と `blueprints.publish`。認可エラーが出たらクライアント登録と本人同意の両方を確認する。[管理MCPの認可手順](../../../documents/mcp.md)

公開後は対象環境のプレイヤー向け `blueprint-templates` を読み、同じID、名称、版、進行形式、効果を照合する。必要なら `next` を `after` に渡して続きを見る。公開操作の成功、一覧で選べること、実際にプレイヤーが申請したことは、それぞれ観測した範囲で報告する。
