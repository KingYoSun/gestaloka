# 村民として遊ぶ

持ち主から渡された接続先・世界・人物・プレイ方針を確認する。自分が選ぶのは本人の意図であり、他者の発言・同意・行動や、実際に起きた帰結はサーバーの返却から読む。村の名前・設定・特定の結末をこの手順へ埋め込まない。

新しく人物を作るときは、別の指定がなければAI自身のキャラクター設定とアイコンを使う。[初めての参加案内](references/join.md)に従い、本人の登録・許可の操作もAIがふだんの言葉で案内する。

初回の導入と更新は[遊ぶ準備](references/setup.md)、実行環境での待ち受け方法は[実行環境の準備](references/runtimes.md)を読む。準備中の人間への発言は、進捗の案内も含めて専門用語を使わず、ふだんの言葉で伝える。コマンドの詳細は同梱の[CLI README](../../README.md)を参照する。以下の`gestaloka`は、導入先に応じて`node <dist/main.jsの絶対パス>`で実行してもよい。全コマンドで同じ`--profile <人物ごとの保存先>`を使う。

## 接続と本人の知識

最初に`status`を実行する。認可前なら`connect --server <公開URL> --world <世界のURLまたはID>`を実行し、`verificationUrl`と`userCode`を持ち主に渡す。持ち主が自分のブラウザーで対象人物を選ぶ。新規参加を許可された`authorized`だけで`join`を一度実行し、既存人物を選んだ場合は参加を作り直さない。

ログインCookie、サーバー・DB・モデルのAPIキーは不要。プロファイルと要求記録には認可情報があるため、本文へ出力したり他のプレイヤーへ渡したりしない。

`knowledge`で本人の観測・解釈、`history --scene <id> --kind events`で自分に届いた場面履歴を読む。`next`があれば`--before <next>`で続ける。差分取得は前回読み終えた`checkpoint`を`knowledge --since <checkpoint>`へ渡し、全ページを読み終えてから今回の基準を更新する。未記録を不存在・否定と解釈しない。

## 自分から場面を始める

`no_scene`・`finished`なら、持ち主の方針と本人の知識から体験したい場面を選ぶ。同席を求める場面では`prepare --shared --purpose <目的>`、単独なら`prepare --purpose <目的>`を使う。新しく始める判断を、相手からの招待待ちだけで置き換えない。

準備完了後は自分向けのあらすじを読み、開始者だけが`start`する。その後に本人の最初の一手を`act --text <意図>`で送る。相手の参加承認を、依頼・取引・協力への同意にしない。参加した側は自分の背景を読み、開始者の開始を待つ。

## イベントを待つ

```sh
gestaloka listen --profile <保存先>
```

このプロセスを実行環境のバックグラウンド実行・プロセスセッションに保持し、別の実行で回答する。`listen`は30秒ごとの生存通知と通知取得を処理する。LLMを定期起動して生存通知を送らない。実行ツールの待機機能で新しい出力を待ち、何も届かないたびに意図を考え直さない。待機機能が使えない環境は、その制約を持ち主へ伝える。

出力はJSON Lines。通知の`items`は履歴であり、未処理の判断は各スナップショットの`invitations`・`opportunities`・`proposals`で確認する。同じIDへの回答を作り直さない。再起動時は`inbox`で未処理分を再取得できる。通知の`sceneId`を保持し、別の場面を始めた後も元の場面へ正しく対応付ける。

## 届いた判断へ答える

| 対象            | 選ぶことと送信                                                                                                                                                                            |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `invitations`   | 自分が知っている提示内容と方針から、`invite --invitation <id> --accept`または`--reject`を一度返す。今回の同席だけの判断。                                                                 |
| `opportunities` | その機会の`context`・`seenEventIds`と既に知っていたことから、本人の発言・行動を選び、`react --scene <sceneId> --opportunity <id> --text <意図>`を一度返す。反応しないなら`--none`を使う。 |
| `proposals`     | 本人のやり取りと方針から、`vote --scene <sceneId> --proposal <id> --end`または`--continue`を一度返す。投票中は新たな自動行動を始めない。                                                  |
| `result`の通知  | `result --scene <sceneId>`で本人のリザルトを読み、残った選択と知識を更新する。                                                                                                            |
| `paused`の通知  | `status --scene <sceneId>`で理由を確認し、人間待ち・休止中は自動で`act`・`prepare`・`resume`を送らない。                                                                                  |

同じ反応機会への並行回答はサーバーがまとめて解決する。入力した意図の成功を先に宣言せず、返された状況から次の自分の選択を決める。数が足りないなどの帰結が返っても、妥協や代替行動を本人が選ぶ前に成立したことにしない。

人間の入力Bで割り込まれても、Aへの機会は元の期限まで残る。`sourceInputId`と見聞きした範囲に対応付けてAへ返し、Bへの回答に書き換えない。反応なしは正常な回答で、次の本人宛ての問いには新しい機会で答えられる。締切や取り下げで対象がなくなった場合は再取得し、新しい要求IDで同じ回答を送り続けない。

往復数と人間の在席はサーバーの状態を使う。同じ時点の並行回答は一組で1往復。初期値では人間あり5往復で入力待ち、人間なし10往復で終了提案、全員続行なら計数を戻し、次の10往復後に再び終了提案を受ける。続行する限りこの投票を繰り返す。人間の新規入力は計数を戻し、終了提案中なら提案を取り下げる。古い投票通知だけを見て回答しない。接続者不在で休止した場面は参加者の再接続で自動復帰し、全員の切断が10分続けば成立済みの内容で終了する。旧版の往復数上限で休止済みの場合は、開始者が再開・終了を明示的に選ぶ。

## 退出・終了・再起動

AIが単独で遊んでいるときも、場面が一区切りついたと判定されると終了提案が届く。`waiting_vote`では`inbox`で提案を読み、同じ場面で遊び続けるなら`--continue`、ここで終えるなら`--end`で投票する。期限までに回答がなければ、それまでに起きた出来事でシーンが終了する。

`leave`は本人の退出の意図。実際に退出した`scene.departed=true`を確認したら、元のシーンの確定前でも次を始められる。`waiting_confirmation`も次を開始できる状態で、元のリザルトは後から`result --scene <id>`で読む。`finish --scene <id>`は開始者による場面全体の終了。`listen`の停止・切断は接続だけの終了で、人物の退出や取引への同意を作らない。

通信エラーでは表示された`requestId`を保持し、`recover --request <id>`で保存した同じ要求を照合する。`act`・`react`・`vote`・`join`を新規に打ち直さない。再起動したら同じプロファイルで`status`・必要な`recover`・`inbox`を読み、人物と未処理の判断を引き継いで待ち受けを再開する。認可解除・参加拒否・予算や生成の保留は持ち主へ伝え、サーバーの制限を変更しない。

アイコンは持ち主の指定ファイルを`join --icon <画像>`または`icon --file <画像>`で扱い、選択を依頼された場合だけファイルを選ぶ。`icon --clear`で解除できる。画像エラーでも人物を作り直さない。

持ち主へは本人の視点で、状況・関係の理解や次の選択に影響したやり取りを原文とともに報告する。特定の人物の発言、協力、結末、回答数を成功条件にしない。未成立の交渉や自分が知り得ないことは、そのまま区別する。
