# 死亡・怪我・治療

人物が怪我をする仕組み、怪我の治し方、死亡したときに起きることをまとめる。判定の流れと申請の形式は[ダイスの判定](dice.md)と[世界への申請](commands.md)を読む。この文書の `outcome` などの項目は、CLI の出力では `result` の下に入る。

## 怪我は状態として残る

怪我や疲れ、拘束といった人物の変化は、本人の**状態**として記録される。状態は `search --kind self` の `material.states` で読める。

- `material.states[].node.text`: 状態の本文（例: 「左腕に浅い切り傷がある」）。
- `material.states[].relation.id`: 状態の関係ID。状態を終えるときに使う。
- `material.states[].relation.period.until`: 期限のある状態だけに入る、終わる時刻（UNIX時刻のミリ秒）。
- `material.states[].relation.text`: `judged` なら、GM が判定の結果として付けた状態である。`location` なら所在で、怪我などの状態ではない。

相手の状態は、同じ場所で `search --kind subject --target <相手のID>` で調べる。相手が読める範囲を狭めた状態は出ない（[コマンド一覧](cli.md)の `viewers`）。

## 怪我を負うとき

怪我は、ダイスの判定を経て残る。発言・移動・受け渡しなど、ダイスを振らない行動では怪我を負わない。

| 起きる場面                                           | 状態が残る人物                 | 読む場所                                                                                                                                |
| ---------------------------------------------------- | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| ほかの人物の対抗行動（`oppose`）が成功した           | 作用を受けた、同席している人物 | 申請者は応答の `outcome.setting.states`（`outcome.success` が `true` のときだけ記録される）。作用を受けた人物は自分の `material.states` |
| 出現個体（インスタントNPC）の行動が成功した          | 作用を受けた人物               | セッションの記録の、その個体の行動の `entries[].result.effectState`。`npc-action` で申請したときは応答の `effectState`                  |
| 自分の作成・対抗の判定が失敗し、さらにファンブルした | 申請した本人                   | `outcome.fumble.success` が `true` のとき、`outcome.setting.fumble.text`。判定が複数ある申請では `outcome.proposals[]` の各判定         |

- 対抗行動とファンブルで残る状態の本文は、GM が書く。出現個体の行動では、行動の結果（`effect.state`）のうち GM が認めた箇所が残る。
- 同意を待たない対抗行動（`oppose`）で相手に残る状態は、GM が返したものだけである。`oppose` の `changes` に相手の状態を書いても記録されない。
- ファンブルは、GM がファンブルの範囲を設定した判定でだけ起きる。世界のファンブルの基準は、運営者が表示を選んだ世界なら `status` の `fumbleCriteria` で読める。`explore`、隠密の判定、乗り物の操縦権の判定、死亡の判定にファンブルはない。
- 自分の状態を `changes` で書くこともできる。この申請は GM が一度判断し、まだ成立していない変化ならダイスで判定する。こうして書いた状態には `judged` の印が付かない。

## 期限のある怪我と、ない怪我

GM は、ファンブルで本人に残る状態と、対抗行動の成功で相手に残る状態に、続く時間（`minutes`、現実の分）を付けることがある。付けるのは、何もしなくても時間の経過で終わる状態だけである。

- **期限のある状態**: `relation.period.until` の時刻を過ぎると、現在の状態から外れる。履歴には残る。
- **期限のない状態**: 次の状態は、終えるまで続く。
  - 自然には治らないと GM が判断した状態（欠損など）
  - 出現個体の行動で残った状態
  - `changes` で書いた状態（関係の `period` に `until` を書いた場合は、その長さで終わる）
  - 期限の仕組みより前に付いた状態

## 怪我を治す

怪我は、状態の関係を終えると治る。

### 自分で終える

治った怪我の関係IDを `changes.endEdges` に入れ、`update` で申請する。

```json
{
  "command": "update",
  "text": "傷口を洗って包帯を巻き、腕の傷の手当てをする",
  "changes": {
    "nodes": [],
    "revisions": [],
    "edges": [],
    "endEdges": ["治したい状態の関係ID"]
  },
  "dependencies": []
}
```

`dependencies` には `search --kind self` が返した依存版を入れる。期限を過ぎて終わった状態を指定すると `WORLD_CHANGED` になる。

この申請は GM が一度判断する。

- GM が、すでに成立した結果の反映や表記の訂正と認めれば、ダイスも SP も使わずに確定する。成立した結果と認められるのは、手当ての結果を本人の状態に記録した成功済みの判定（自分や他人の申請）が、直近の記録にある場合である。発言で手当てをしたと書いただけでは根拠にならない。`materials` を付けた申請は、この扱いにならない。
- まだ治っていない怪我を治す申請は、同じ応答で GM がダイスを設定し、1 SP を使う。成功すると、GM が申請の意図に合うと選んだ状態が終わる。失敗すると状態は終わらず、ファンブルすれば本人に新しい状態が残ることがある。
- 手当ての結果として残る新しい状態（例: 「腕に包帯が巻かれている」）を `changes.nodes`・`changes.edges` に加え、同じ `changes` の `endEdges` に古い傷の関係IDを入れれば、一度の判定で両方が確定する。`operations` と `changes` は同じ申請に並べられない。
- ダイスで判定すると、成功時に GM が手持ちの包帯や薬から使った分を減らすことがある（`outcome.setting.consumes`）。`materials` に薬を指定した申請は必ずダイスで判定し、成功すると指定した薬が減る。薬は手元か今いる場所にある必要があり、足りなければ `MATERIAL_SHORTAGE` になる。
- 確定した終了は、ダイスを振ったときは `outcome.setting.endEdges`、そのまま確定したときは `outcome.endEdges` で確かめる。

手当ての方法や使う道具・薬を `text` に書く。治り方に無理がある申請ほど、GM の判定は厳しくなる。

### ほかの人に治してもらう

治す人は、同じ場所で相手の状態の関係IDを `search --kind subject --target <相手のID>` で読み、次のどれかで申請する。

- **相手の同意を得る（`update`）**: 治す人が `update` の `changes.endEdges` に相手の状態の関係IDを入れて申請する。相手が同じセッションにいて離席していなければ受領の判断が回り、相手が承認すると状態が終わる。GM は審査せず、終了だけの申請はダイスも SP も使わない。相手がいないと `REMOTE_RECEIVING` などで断られる。包帯を巻いた状態など新しい状態を加えると、作成の判定（ダイス、1 SP）を経てから相手の受領に回る。受領の手順は[セッション・手番・受領とチーム](sessions.md)を読む。
- **同意を待たない（`oppose`）**: 治す行動を `text` に書き、終えたい状態の関係IDを `changes.endEdges` に入れる。ダイスに成功すると、GM が申請の意図に合う状態を選んで終える（`outcome.setting.endEdges`）。治療の結果として相手に残る状態も GM が決め（`outcome.setting.states`）、申請者が `changes` に書いた相手の状態は記録されない。
- **同席の出現個体に手当てさせる（`npc-action`）**: `effect` の `targetId` に怪我をした人物、`state` に手当ての結果、`replacesStateId` に置き換える状態の `node.id`（関係IDではない）を書く。成功すると GM が古い状態を選んで終え、`state` のうち GM が認めた箇所が新しい状態として残る。書き方は[NPCの出現・昇格・同行](npcs.md)を読む。

### 時間がたつのを待つ

期限のある状態は、`relation.period.until` を過ぎると自然に外れる。期限の前に早く治したいときは、上の方法で終える。

## 死亡

### 死亡する条件

死亡は、対抗の判定と出現個体の行動の判定で、GM がダイスの設定と一緒に決める。`outcome.setting.fatal` は成功したときに死亡する対象なので、失敗した判定にも出る。死亡が起きるのは、`outcome.success` が `true` のときだけである。

- **プレイヤーとユニークNPC**: 運営者が死亡判定を無効にしていない世界（既定は有効）で、行動の作用を受ける同席中の人物が対象になる。成功した判定の `outcome.setting.fatal` に入っていれば死亡が確定する。
- **出現個体（インスタントNPC）**: 検索で現れた個体は、1体でも個体数を持ち、死亡は `instantReduction` の死亡の数と残数で確定する。個体数を持たない個体（`say --npc` で登場させた個体と古い記録の個体）だけが `fatal` に入る。

人物の死亡は `fatal` でだけ確定する。申請の `changes` で相手を死亡させることはできない。運営者は、世界ごとに死亡の条件文を設定できる。

### 死亡したプレイヤーとユニークNPCに起きること

死亡は**復帰**として扱う。死亡した人物はいなくならず、次のように続ける。

1. 死亡を確定した判定（対抗行動か出現個体の行動）と同じ確定で、世界に設定された場所へ移る。設定がなければ、本人が最初にいた場所へ移る。行き先が定まらないときは、その場にとどまったままセッションから外れる。
2. 元のセッションから外れ、移った先の単独のセッションで続ける。元のセッションと本人のセッションの両方に、死亡による離脱が記録される（隠密で滞在中なら、元のセッションには記録されない）。
3. 同行関係は残ったまま待機（`wait`）に変わり、ついてこない。また一緒に動くには、同じ場所で `companion follow --target <NPCのID>` を使う。離れているなら迎えに行くか `companion move` で呼び戻す（[NPCの出現・昇格・同行](npcs.md)）。死亡したNPCがだれかに追従していた場合も、その同行は待機になる。
4. 次の状態は、復帰後の現在の状態に残らない。履歴には残る。
   - GM が判定の結果として付けた状態（対抗行動の成功で GM が返した状態、ファンブル、出現個体の行動で残った状態）
   - 期限のある状態
   - 死亡を確定した判定で付いた状態
5. 次の状態は残る。
   - 申請の `changes` に書いて付いた状態。ダイスで判定されたものも、ほかの人が `update` で付けて承認されたものも含む。
   - 判定の印の仕組みより前に付いた、期限のない状態。

死亡によって持ち物が落ちたり失われたりはしない。死亡を確定した同じ行動で奪われた物は、その結果どおり相手へ移る。死亡の経緯は出来事の記録と目撃に残るので、周りの人物は死亡したことを知りうる。

復帰したら、`search --kind self` で所在と状態を確かめる。元の場所の人物とまた話すには、同じ場所へ移動して `contact` し直す。

### 出現個体の死亡

出現個体は、死亡すると同席者の一覧から外れる。一団なら残数が減り、0になると外れる。世界が設定していれば、死亡した数に応じてその場に品が残ることがある。`say --npc` で登場させた個体は品を残さない。読み方は[NPCの出現・昇格・同行](npcs.md)を参照する。

## よくある疑問

- **治ったのに怪我が残っている**: 期限のない状態は自然には外れない。「自分で終える」の手順で、関係IDを `endEdges` に入れて申請する。
- **相手に負わせる怪我を自分で決めたい**: 同意を待たない `oppose` ではできない。相手に残る状態は GM が決め、`outcome.setting.states` で読める。相手の同意を得る `update` なら、相手が承認した状態が残る。
- **死亡した後も怪我が残っている**: 死亡で終わるのは、GM が判定の結果として付けた状態と、期限のある状態だけである。`changes` で書いた状態と、判定の印の仕組みより前に付いた期限のない状態は残る。治っているなら「自分で終える」の手順で終える。仕組みの導入前の死亡で残った状態は、`report` で運営者に知らせる。
