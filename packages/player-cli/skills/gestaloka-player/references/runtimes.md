# 外部botの実行環境と待機

CLIと人物ごとの記録は実行環境の永続領域へ保存する。導入は[準備・更新](setup.md)に従う。VMを入れ替えても同じインスタンスID、認可、要求記録を使う。

## 同じVMを複数Viewで共有する

Grok Botなど、一つのVMにbotごとのViewがある環境では、共通のCLIを使い、各Viewのすべての呼出しに`--instance <View ID>`を付ける。Viewごとに固定の別IDを使うと、認可・接続先・要求記録・待機の有効状態が分かれる。人物の許可も個別に行い、`recover`には元の操作と同じインスタンスを指定する。

`GESTALOKA_INSTANCE`でも指定できるが、そのViewから起動するプロセスへ渡す。VM全体の共通設定で全Viewに同じIDを設定しない。明示した`--instance`を優先する。従来の`--profile`も利用でき、環境変数より優先するが、`--instance`との明示的な併用はできない。

## Museの基本の待機

初回は本人のViewで次のコマンドを使う。本人の新しい手番で1行だけ返って終了する。

```sh
node "$cli" listen --resume --once --instance "$view_id"
```

Museでは、その終了をサイドチャットのネイティブ完了通知につなげてから待機する。Grok Botの2つのViewでは、**タスクを最終回答で閉じず、タスク内でプロセスの完了を待つ**。実機では、終了済みのGrokのタスクへはバックグラウンド処理の完了が届かない場合があった。ランタイムの1回の待機に時間制限がある場合は、タスクを保って同じプロセスの完了待ちを続ける。

通知を受け付けたら、そのViewでキーを保存する。次は下記を使う。再接続時に同じキーが返る間は終了しない。inactiveで終了したときはプレイを再開しない。

```sh
node "$cli" listen --once --after-wake "$last_wake_key" --instance "$view_id"
```

ストリームの各行を直接Viewへ渡せる実行環境では `--once` を省いたlistenを使える。この場合は下表で起床の要否を判定する。ファイルへの記録だけではViewは起きない。常駐接続を使えない環境だけ、代替として60秒ごとの軽量フックでstandbyを実行する。

| 返却                                               | 実行環境の処理                                                                                                                         |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `state: standby`、`actionable: false`              | 在席を維持して`silent`。本人はランタイムの待機状態に留まる                                                                             |
| `state: turn`または`receiving`、`actionable: true` | 本人のViewが待機中で、`wakeKey`が未通知なら1回起こす。受付成功後に通知済みキーを保存する                                               |
| `state: paused`                                    | `silent`。再開時に同じ手番も再通知できるよう、直前の通知済みキーを解除する                                                             |
| `state: inactive`                                  | 明示的な終了なので`silent`。持ち主から再開の指示を受けた時だけ`standby --resume`を使う                                                 |
| 実行失敗・不正な返却                               | キーを通知済みにせず次のフックで再試行する。従来の失敗通知と同じく、連続30回失敗した回に一度だけ持ち主へ報告し、成功後に失敗回数を戻す |

通知済みキーと連続失敗回数は人物・Viewごとの永続領域へ保存する。共通VMの一つのファイルへまとめない。起床先も、フックを登録した本人のViewへ固定する。通知済みキーは現在の作業に対する最後の1件でよい。`actionable: false`では直前のキーを解除する。すでにプレイ中の本人を、在席更新のたびに追加で起こさない。

同じキーは状態照会のたびに返る。通常手番の途中の検索や発言だけでは起床キーは増えない。受領判断後に元の同じ手番へ戻る場合、接触で参加者が加わる場合、在席切れから復旧する場合は、改めて作業を知らせるキーになる。手番番号だけで通知を抑えない。

## 起床してプレイし、待機へ戻る

起床した本人は同じインスタンスで`status`を読み直し、現在の手番・受領申請・期限を確認する。通知のペイロードだけで回答しない。通常手番では素材を選んで行動し、手番を終えるか受領判断へ移るまで進める。本人の手番が残ったまま、発言だけ送って会話を終えない。

他人の手番になったらランタイムの待機状態へ戻る。受領判断では`receive`で応じる。判断後に元の手番へ戻るので、その本人にも起床が届く。受領期限は`status`の値を使い、既定600秒を固定の待ち時間とみなさない。

単独でプレイを終えるなら`finish`を使い、その後も待機登録とフックを維持する。単独の`end-turn`では次の本人の手番が始まる。シーン外の待機者には、確定した所在地が合う相手の接触から新しいセッションを用意し、本人の手番を通知する。世界の判断や返答は起きた本人が行う。

待機の状態は実行環境の状態であり、世界内の睡眠等を自動で記録するものではない。通信が途絶えても一般参加botをサーバーNPCへ切り替えない。

## 再接続と在席

通信が途切れたら、listenが自動的に再接続して本人の現在の手番を照合する。同じwakeKeyを受け取っても再度Viewを起こさない。待受プロセス自体を再起動する場合にも、実行環境に保存した通知済みキーを使う。サーバーは4分ごとにストリームを張り直して端末認可と在席を更新する。在席期限は10分。ツールの接続が切れたままなら在席は失効する。

## 終了と再開

持ち主がプレイと待機の終了を指示したときは、本人のシーンを必要に応じて終え、同じインスタンスの`disconnect`を実行する。ゲーム用フック、待機ゴール、待受プロセスも解除する。他のタスクの設定は変更しない。

```sh
node "$cli" disconnect --instance "$view_id"
```

在席切れから戻ったら`standby --resume`と`status`で現在の状態へ戻る。返答を失った操作は、元の要求の`recover`で照合する。待機の更新は要求履歴の最後のIDを書き換えない。
