# 世界への申請

`gestaloka play --file <UTF-8のJSONファイル>`でPlayCommandを送る。CLIが要求IDを作成・保存する。返却を失った場合は`recover`で同じ要求を照合する。下記の識別子は実際に本人が取得したものへ置き換える。

ダイスを振る申請・判定の材料・エラーごとの原因は[ダイスの判定](dice.md)を読む。`text`や`basis`に書いた内容は記述として記録されるだけで、物を持つ存在は変わらない。物を持つ存在は`create`の`holder`と`move`の`to`で指定する。

## 時間差で受け取る申請

`memo` や既存メモの本文を改訂する `update`、物品の `move` だけの `update` に、UTCのISO日時で `deferredUntil` を指定できる。相手が同席していない場合も、本人の通常手番で送れる。受領者は `applications` で申請の本文・差分・実時刻の期限を読み、`receive --application <ID> --accept` または `--reject` で判断する。申請者は `withdraw --application <ID>` で取り下げられる。照会・受領判断・取り下げに通常枠はかからない。

物品やメモは受領が揃った時点で、承認した条件が有効なら確定する。結果は当事者の `notices` に届く。

## 場所に公開する交換

本人が登録した保管先（家や場所）に在庫を置き、その場所で次の形式を `play --file` から送る。手に持つ箱は持ち物なので、在庫置き場にはならない。支払い品の系列IDは本人検索の物品に付く `seriesId` で確認できる。

```json
{
  "command": "offer",
  "storageId": "その場所にある保管先のID",
  "itemId": "保管先にある品のID",
  "count": 1,
  "paymentSeriesId": "支払い品の系列ID",
  "paymentLabel": "銅貨",
  "paymentCount": 2,
  "text": "銅貨2枚で焼き菓子を1つどうぞ"
}
```

買い手は同じ場所の `search --kind surroundings` に出た `exchangeOffers` を読み、`exchange --offer <交換ID> --payment <物品ID>` で受領する。支払いには、本人が手にしている品の系列と個数が合う必要がある。品物は買い手の手元、代価は売り手の保管先に移る。公開した交換条件は `applications` で確認し、`withdraw --application <交換ID>` で取り下げられる。

## 用途別の更新

`dependencies`には素材検索が返した依存版を渡す。`operations`は既存の内部処理を使い、受理した差分だけが原子的に確定する。

```json
{
  "command": "update",
  "text": "取得した場所へ移動する",
  "operations": [
    {
      "type": "locate",
      "subjectId": "本人のID",
      "text": "場所の説明",
      "aboutIds": ["直接滞在する場所のID"],
      "directPlaceId": "直接滞在する場所のID"
    }
  ],
  "dependencies": []
}
```

| type           | 引数                                     | 意味                         |
| -------------- | ---------------------------------------- | ---------------------------- |
| locate         | subjectId, text, aboutIds, directPlaceId | 本人または同行者の所在地     |
| create         | label, count任意, holder, basis          | 新しい物品。holderの物になる |
| move           | item, from, to, count任意, basis         | 受け渡し。toの物になる       |
| grant / revoke | person, storage。grantにはbasis          | 家・場所の保管先の登録       |
| learn          | person, text, basis                      | 技能とできる範囲             |
| update         | id, text任意, count任意, basis任意       | 物品の呼称・個数、技能の内容 |
| remove         | id, count任意                            | 消費・破棄・技能の喪失       |

### 物の受け渡し

物品は、持っている存在の物である。渡す・売る・払う・贈る・貸す・返す・置く・預けるは、どれも `move` で表す。`from` に今持っている存在、`to` に受け取る人物・場所・保管先・箱を指定する。受け取った存在の物になり、持ち主と置き場所が分かれることはない。

| したいこと                             | 申請                                                      | 受領・条件                                 |
| -------------------------------------- | --------------------------------------------------------- | ------------------------------------------ |
| 相手に渡す（贈る・払う・貸す・返す）   | `move`（`from` 本人、`to` 相手）                          | 相手の受領。同じセッションにいる必要がある |
| 売る・買う                             | 品物と代価の2つの `move` を1件の `update` に並べる        | 相手の受領。両方が同時に成立する           |
| 落ちている物を拾う                     | `move`（`from` null、`to` 本人）                          | 受領なし。同じ場所にいる必要がある         |
| 誰も登録していない場所に置く・拾う     | `move`（`to` 場所、または `from` 場所）                   | 受領なし。同じ場所にいる必要がある         |
| 自分が登録した保管先に預ける・取り出す | `move`（`to` 保管先、または `from` 保管先）               | 受領なし。保管先の場所にいる必要がある     |
| 他人の保管先に置く                     | `move`（`to` 保管先）                                     | 登録した人物の受領                         |
| 他人の保管先から取り出す               | できない                                                  | 登録した人物に渡してもらう                 |
| 手に持つ箱や袋に出し入れする           | `move`（`to` 箱、または `from` 箱）                       | 受領なし。場所を問わない                   |
| 不在の相手に置き手紙・置き土産をする   | `move` に `deferredUntil`（上記「時間差で受け取る申請」） | 相手が戻ってから判断する                   |

- 貸し借りや預かりの約束は、`basis` に書くか `memo` に残す。システムは返却を守らないので、借りた物も、持っている人が動かせる。
- 保管先とその中身は、`search --kind self` の `material.belongings.storages` で読む。登録した保管先の中身は、離れていても読める。
- 物を置いたことを `say` や `changes` の記述で書いても、物品の所在は変わらない。所在は `move` で移す。
- 判断できる人物の記録がない箱や存在に物を移そうとすると `AUTHORITY_REQUIRED`、受領する人物が同じセッションにいないと `REMOTE_RECEIVING` が返る。どちらもメッセージに対象の名前とIDが入る。

#### 渡す・払う・贈る

```json
{
  "command": "update",
  "text": "ランプを相手へ渡す",
  "operations": [
    {
      "type": "move",
      "item": "ランプのID",
      "from": "本人のID",
      "to": "相手のID",
      "basis": "贈り物として渡した"
    }
  ],
  "dependencies": []
}
```

代金だけを払うときも同じ形で、`item` に代価（銀貨など）、`count` に払う数を指定する。

#### 売る・買う

品物と代価の交換は、1件の `update` にまとめて申請する。品物を渡す `move` と代価を受け取る `move` を並べると、相手の受領で両方が同時に確定する。片方だけが成立することはない。買い取りは、品物と代価の向きを逆にする。品物を渡してから代金を別に頼むと、払われないまま終わることがある。

```json
{
  "command": "update",
  "text": "パンを2個、銅貨6枚で売る",
  "operations": [
    {
      "type": "move",
      "item": "パンのID",
      "from": "本人のID",
      "to": "買い手のID",
      "count": 2,
      "basis": "売った"
    },
    {
      "type": "move",
      "item": "買い手の銅貨のID",
      "from": "買い手のID",
      "to": "本人のID",
      "count": 6,
      "basis": "代価"
    }
  ],
  "dependencies": []
}
```

- 相手が手にしている物のIDは、`search --kind surroundings` の `subjects[].held` で読む。保管先に置いてある物は、相手が手に持ってから申請する。
- 受領判断は通常の手番の順に割り込んで相手へ回るので、相手の手番を待つ必要はない。相手は期限（`status` の `receiving.deadline`、初期値は600秒）までに `receive` で判断する。
- 相手が却下した、期限までに判断しなかった、セッションを離れた場合は、申請が終わり、何も動かない。申請者の通常枠が残っていれば、申請者の元の手番に戻る。結果は `status` の手番記録と待受の `receiptResult` で読める。期限切れのあとは、相手が戻ってから申請し直す。
- 相手が同じセッションにいないと `REMOTE_RECEIVING` が返り、通常枠は使わない。先に `contact` で合流する。
- 値段を決める基準は世界にはない。売り値は当事者が決める。以前の取引を手がかりにするなら、成立した値段を `memo` に残しておく。

#### 置き手紙・置き土産

相手が不在でも、`move` だけの `update` に `deferredUntil` を付ければ送れる。相手が戻って `receive --accept` で受け取った時点で、相手の物になる。相手の家（相手が登録した保管先）に置くときも、`to` に家を指定して同じ形で送る。

#### 保管先と店

家や場所を自分の保管先にするには、その場所で `grant`（`person` に本人、`storage` に家や場所）を申請する。誰も登録していない家・場所の登録は、新しく得る申請としてダイスで判定する。GMは、その場所を自分のものにする事情（建てた、借りた、譲られたなど）を `text` から読む。誰かが登録している場所は、その人物の受領が要る。家族や店の仲間にも使わせるときは、相手を `person` にして `grant` する。

店を開くときは、店にする家や場所を登録し、在庫を `move` で保管先へ置く。その場所で公開交換を出せば、売り手が離れている間も、買い手が `exchange` で買える（上記「場所に公開する交換」）。手に持つ箱は持ち物なので、在庫置き場にはならない。

### 物品の個数

物品は個数（`count`）を持てる。個数のない物品は、数えないひとまとまりとして扱う。本人の持ち物と個数は`search --kind self`の`material.belongings`で読む。

- `move`に`count`を指定すると、その個数だけを渡す・置く・預ける。残りは元の物品に残る。省くと全部が対象になる。
- 渡した先に、呼称と系列が同じ個数つきの物品があれば、その個数に足される。なければ、渡した個数の物品が新しくできる。受け取った側は自分の`belongings`でIDを確かめる。
- `remove`に`count`を指定すると、その個数だけ減る。全部なくなれば持ち物から消える。
- `update`の`count`で個数を書き換えられる。減らすのは本人の判断でできる。増やす・個数のない物品に新しく付けるときは、新しい物を得る申請として下記の新規作成と同じダイスで判定する。
- 個数のない物品に`move`・`remove`の`count`は指定できない。

### ダイスの成功で減る物品

GMがダイスを設定する申請（新規作成、個数を増やす更新、対抗行動）では、GMが同じ判定で、成功したときに減る物品も決める。対象は本人が手に持つ物だけで、保管先に置いた物は減らない。応答の`outcome.setting.consumes`に、物品のID・呼称・減る個数が入る。成功すると申請と同じ確定で減り、失敗すれば減らない。申請自身が`operations`で動かす・減らす物品は、GMの判定からは外れる。新しい場所の`explore`では減らない。

### 物を使って何かを変える

塗料で壁を塗る、木材で柵を建てる、食材で料理するなど、手元の物を使って何かを変えたときは、**変わった結果の状態**を `changes` で申請する。使う物は `remove` で消さずに、手に持ったまま申請する。ダイスが成功すると、GM が手元の物から使った分を選んで減らす（`outcome.setting.consumes`）。

`remove` で物を消すだけの申請では、物が減るだけで、結果は記録されない。`text` に「壁を紫に塗った」と書いても、壁の状態は変わらない。

```json
{
  "command": "update",
  "text": "手に持つ青い塗料と刷毛で、家の柵を青く塗る",
  "changes": {
    "nodes": [
      {
        "id": "新しく作る状態のID",
        "kind": "script",
        "text": "家の柵は青く塗られている。"
      }
    ],
    "revisions": [],
    "edges": [
      {
        "id": "新しく作る関係のID",
        "kind": "status",
        "role": "content",
        "source": "家のID",
        "target": "新しく作る状態のID",
        "period": { "from": 0 }
      }
    ],
    "endEdges": ["当てはまらなくなった古い状態の関係のID"]
  },
  "dependencies": []
}
```

- 新しい状態のIDと関係のIDは、申請ごとに新しいUUIDを作る。
- 古い状態（「柵は白い」など）が残っていれば、`endEdges` にその関係のIDを入れて終える。家や場所の状態と関係のIDは、`search --kind subject --target <家のID>` で読める。
- 新しい状態を作る申請なので、ダイスで判定する。失敗すれば何も変わらず、物も減らない。
- 料理や工作のように新しい物ができるときは、`operations` の `create` で作る。こちらも、材料を手に持っておけば、成功したときに GM が減らす。

### 時間をかけて物品を得る

その場にない物を取り寄せる、手間をかけて作る、育つのを待つなど、すぐには手に入らない物品は、かける時間を指定して申請できる。`update` に `waitMinutes`（実時間の分）を加える。世界の時間は実時間と同じ速さで進むものとして数える。

```json
{
  "command": "update",
  "text": "隣町の牧場からミルクを取り寄せる。銀貨で払い、荷車で2日かけて運んでもらう",
  "operations": [
    {
      "type": "create",
      "label": "ミルク",
      "count": 10,
      "holder": "本人または保管先のID",
      "basis": "隣町の牧場から取り寄せた"
    }
  ],
  "waitMinutes": 2880,
  "dependencies": []
}
```

- かける時間は、GMがダイスを設定する材料になる。時間をかけるほど成立しやすい申請では、かける時間に応じて判定が緩くなる。すぐに成立させるには無理がある物ほど、長い時間を指定する意味がある。`text` には、何をどう手に入れるかと、その時間で足りる理由を書く。
- 指定できるのは、物品の `create` だけを並べた申請に限る。`holder` に同席者を指定するなど、他の参加者の受領が必要な申請には指定できない。どちらも `WAIT_NOT_APPLICABLE` が返り、通常枠は使わない。
- ダイスは申請時に一度だけ振る。失敗すると何も作られず、通常枠を1回使う。成功すると、GMが選んだ代価（`outcome.setting.consumes`）が同じ確定で減り、応答の `arrival.dueAt` に物品が届く時刻が入る。
- 物品は届く時刻を過ぎてから、`holder` に指定した存在のもとに成立する。それまでは持ち物に現れない。届く予定は `search --kind self` の `arriving`（申請の文、物品の呼称と個数、届く時刻）で読める。人に約束するときは、この予定を確かめてから伝える。
- 届くと本人あての通知ができる。`gestaloka notices` で読む。届いた物品を人へ渡すには、`move` を申請する。

他の参加者の受領が必要なら、返却はreceivingとなる。同じセッションの受領者へ判断が回り、全員の受入後に確定する。セッション外の受領者には送れない。

同席者と一緒に移るときは、本人と同行者ごとに`locate`を並べて一つの`update`で申請する。同行者には受領判断が回る。所在の変更だけの申請では、却下した同行者は移動せず、全員の判断がそろった時点で申請者と承認した人の移動が確定する。移動しなかった同席者がいれば、移動が確定した時点で別のセッションに分かれる。

更新では`operations`の代わりに`changes`で自由な差分を申請できます。既存の状態を終えて新しい性質・関係を記録する場合にも使えます。対抗行動でも同じ二つの形式を使い、特定の行動の一覧には限定しません。

### 本人の呼称と状態を改める

本人の呼称と、本人についての状態（外見・性格・経歴などの記述）は、`update`の`changes`で改める。`operations`の`update`が扱うのは物品と技能だけで、本人や状態のIDを指定すると`BELONGING_NOT_RECORDED`が返る。

`search --kind self`の`material.states`で、状態ごとの本文（`node`）と本人との関係（`relation`）を読む。本文を改めるときは、`revisions`に取得済みの`id`・`kind`と新しい`text`を指定する。本人の状態だけの改訂は、受領もダイスもなく確定する。

```json
{
  "command": "update",
  "text": "髪を短く切った",
  "changes": {
    "nodes": [],
    "revisions": [
      { "id": "状態のID", "kind": "script", "text": "黒い髪を短く切っている" }
    ],
    "edges": [],
    "endEdges": []
  },
  "dependencies": []
}
```

- 呼称を改めるときは、`revisions`に`material.node`の`id`と`"kind": "existence"`、新しい`text`を指定する。
- 当てはまらなくなった状態を終えるときは、`endEdges`に`relation`の`id`を指定する。
- 新しい状態を加えるときは、下記の「その他の作成」に従う。新規作成としてダイスで判定する。

## 新規作成

### メモノード

```json
{
  "command": "memo",
  "text": "見聞きした色や音を自由に並べるノート",
  "participants": ["関係する人物のID"],
  "dependencies": []
}
```

本文の用途は限定しない。メモは`kind: "script", type: "memo"`で保存し、関係する人物からの`has`で関連付ける。本人は自動で含まれる。本人以外には受領判断が回り、全員の受入後に確定する。参加者を指定しなければ本人だけに関連付ける。セッション外への申請は既存の受領と同じく即時エラーになる。

`search --kind memos`は、本人に関連付いた本文・人物・依存版を返す。更新は`update`の`changes.revisions`へ、取得済みのid・kind・typeと新しいtextを指定する。他の関係者の受領が必要になる。受領はメモを関連付ける手続きで、本文の主張をすべて世界の事実へ変換するものではない。

### その他の作成

自由な性質・関係を新しく記録する場合は、`command: "create"`、`text`、`changes`、`dependencies`を指定する。`changes`はnodes・revisions・edges・endEdgesを持つ既存のChange形式で、新規作成ではrevisionsとendEdgesを空にする。物品を持つこと・保管先・技能・所在地は用途別の更新を使う。通常の発言と移動など規則で判断できる作成はGMを呼ばない。判断が残る作成では、GMが世界の基準に従ってダイスを設定し、サーバーが一度だけ振る。物品の `create`、技能の `learn`、`say` の `instantNpcs` も同じ扱いになる。応答の `outcome` に成否・ダイス設定・出目が入る。失敗しても行動として記録されて通常枠を1回使い、何も作られない。`say` では発言だけが記録され、`instantNpcs` は空で返る。同じ要求の再送は同じ結果を返す。

異なる生成案をまとめるには、`play --file batch.json` で次の形式を送る。`proposals` の各案には `text` と、単発の申請と同じ `changes` または `operations` を指定する。最大5案で、探索は単発の `explore` を使う。素材は案の指定順に使う。先の案が失敗すれば次の案に使え、成功して残りが足りなくなった案には、ダイスを振らず `MATERIAL_SHORTAGE` を返す。

```json
{
  "command": "create-batch",
  "dependencies": [],
  "proposals": [
    {
      "text": "端布から袋を縫う",
      "operations": [
        {
          "type": "create",
          "label": "布袋",
          "holder": "<本人のID>",
          "basis": "端布を縫った"
        }
      ]
    },
    {
      "text": "糸を編んで紐にする",
      "operations": [
        {
          "type": "create",
          "label": "組紐",
          "holder": "<本人のID>",
          "basis": "糸を編んだ"
        }
      ]
    }
  ]
}
```

`outcome.proposals` に申請順に結果が入り、成功した案だけ生成物と素材消費が確定する。受領が必要な変更は従来どおり受領後に確定する。`spentSp` はその要求IDで消費したSPで、同じ要求を再送すると保存済みの結果が返る。全案が失敗しても新しく振れば1 SP、すべてが前の出目の再利用なら0 SP。`status` の `dailySp.remaining` が残量、`dailySp.resetsAt` が次の回復時刻である。日次の100 SPは日本時間の毎日0時に回復する。

GMがダイスを設定するときに読む材料は、世界の前提、申請の`text`と`changes`、申請者と申請が触れる対象の記録（状態と持ち物）である。セッションでの会話は渡らない。根拠にしたい物・人物・場所は、`changes`の関係で既存のIDを参照する。`text`には、何を使って何を得ようとするかを書く。運営者が表示を選んだ世界では、`status`の`creationCriteria`で世界の基準を申請の前に読める。

同じ手番でダイスに失敗した申請を、言い回しや細部だけ変えて出し直すと、同じ試みとして前回の設定と出目がそのまま返る。通常枠は1回使い、応答の`outcome.repeated`が`true`になる。別の対象や別の結果を求める申請は、これまでどおり新しく判定される。次の手番からは、同じ内容でも新しい試みとして判定される。この扱いは、運営者が判断モデルを設定した環境で働く。

## 新しい場所

まだ記録されていない場所へ行きたいときは、`explore`で場所の追加を申請する。通常の`create`とは別の操作で、接続元の場所が必須になる。

```sh
gestaloka explore --from <接続元の場所ID> --label <場所の呼び名> --text <場所の様子と、接続元からの行き方>
```

`play --file`で送る場合は次の形になる。

```json
{
  "command": "explore",
  "fromId": "接続元の場所のID",
  "label": "森の奥の沢",
  "text": "ぶー森の小道を奥へ進むと、浅い沢に出る。",
  "dependencies": []
}
```

接続元には、本人の現在の所在地にある場所を指定する。`search --kind self`または`surroundings`の`material.locations[].aboutIds`にあるIDが使える。離れた場所を接続元にはできない。

GMは接続元から見た妥当性でダイスを設定し、サーバーが一度だけ振る。応答の`outcome`に成否・ダイス設定・出目が入る。成功すると`placeId`に新しい場所のIDが返り、`update`の`locate`でそこへ移動できる。接続元と新しい場所には同じ記述が付き、どちらを`search --kind subject`で調べても、相手の名前とIDを`about`から読める。後から来た人物も同じ手がかりで行き来できる。どちらの場所に直接滞在していても、`search --kind surroundings`の`material.routes`に相手の名前とIDが出る。`routes`は移動先の手がかりで、載っていない場所へも、検索結果で受け取ったIDなら`locate`で移動を申請できる。新しい場所は、接続元にいる間も`search --kind subject`で調べられる。

既にある場所と同じ呼び名（`label`）では申請できない。`EXPLORE_NAME_TAKEN`が返り、メッセージに先にある場所のIDが入る。GMは呼ばれず、通常枠も使わない。その場所を`search --kind subject`で調べるか、別の呼び名で申請する。

失敗しても行動として記録されて通常枠を1回使い、場所は作られない。同じ要求の再送は同じ結果を返す。

## 受領を経ない対抗行動

```json
{
  "command": "oppose",
  "text": "相手が持つ品を奪おうとする",
  "operations": [
    {
      "type": "move",
      "item": "対象のID",
      "from": "今持っている存在のID",
      "to": "本人のID",
      "basis": "対抗行動"
    }
  ],
  "dependencies": []
}
```

本人の解釈や持ち物の破棄は通常の更新で扱う。対抗行動の前提となる対象と、それを持つ存在が記録と合わなければ失敗する。外界に作用する対抗行動の関係を構築できる場合はGMがダイスを設定し、サーバーが抽選して結果を保存する。出目と結果を返却から読み、失敗した同じ要求を再送しても振り直さない。

同席している出現個体（インスタントNPC）へ作用するときは、`operations`と`changes`の代わりに`effect`を指定する。`targetId`には同席者一覧にある個体のIDを入れる。

```json
{
  "command": "oppose",
  "text": "鳥に石を投げる",
  "effect": { "targetId": "個体のID", "state": "石が当たる" },
  "dependencies": []
}
```

同じ場所にいる個体ならGMがダイスを設定する。GMは同じ判定で、成功したときに個体が死亡するかも決める。死亡する個体のIDは`outcome.setting.fatal`に入る。成功して死亡した個体は同席者一覧から外れ、以後は行動しない。世界にドロップが設定されていれば、応答の`appearances`にその場に残った物が返る。物品のドロップは、同じ物がいくつ落ちても1つの物品にまとまり、`appearances[].count`に個数が入る。残った物は検索による出現と同じ手順で拾える。`move`に`count`を指定すると一部だけを拾え、残りはその場に残る。失敗した試みも出来事として同席者に届く。`npc-action`の`effect.targetId`にも個体のIDを指定できる。

検索で一度に出現した一団は一つのIDを持つ。現在数は同席者の `characters[].count` で確認できる。一団へ働きかけるときは一団のIDを指定し、試みを文章で伝える。死亡や分離が成立すると `instantReduction` に変化した数と残数が返る。分かれて同席に残った個体は `appearances` に新しいIDで返る。分離の結果が1体なら、分離の要求IDと個体番号を指定して `promote-npc` で昇格申請できる。

運営者が死亡判定を有効にしている世界では、同席しているプレイヤーとユニークNPCも同じ判定の対象になる。対抗行動が成功し、GMが死亡と判定した人物（`outcome.setting.fatal`）は、セッションから外れて世界に設定された場所か本人の最初の所在地へ移る。本人が対象になった場合も同じで、移った先の単独のセッションで続ける。`search --kind self`で所在を確かめ、また話すには同じ場所で`contact`し直す。

## 設計図で建てる・開店する

各操作は `play --file action.json` で送る。`blueprint-templates` の `templates` で公開版の ID と効果を確認し、欲しい効果のテンプレートを選ぶ。建築は道から入れる場所と店主の保管先を作る。開店は指定場所の在庫を交換に出す。両方のテンプレートでは、先に入店と保管ができ、在庫が揃ってから営業が始まる。

`blueprint-propose` の `plan` に `templateId`、`placeId`、`keeperId`、`description` を入れる。建築の場合、`placeId` は接続元の場所、既存店で開店する場合は店主が登録した保管先。現地に移動して申請する。

テンプレートの応答に `materials` がある場合は、その材料と道具を使う。申請の `building` には建屋の `label` を書く。MCPで作った下書きは、発祥の世界で原案者と指定された試遊者が、受け取ったIDを `templateId` に指定して試せる。

| テンプレート     | 追加する項目                                                                                                                                                                                        |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `build`          | `building` に建屋の `label` を書く。テンプレートに材料の指定がなければ `materials` に、品の呼称 `label`、必要数 `count`、消費するなら `usage: "consume"`、使用後に残すなら `usage: "tool"` を書く。 |
| `open`           | `shop.stock` に商品ごとの `itemId`、初期在庫数 `stockCount`、一回に売る数 `count`、代価の `paymentSeriesId`、`paymentLabel`、`paymentCount`、掲示文 `text` を書く。                                 |
| `build-and-open` | `building` と `shop` の両方を書く。                                                                                                                                                                 |

発案者以外を店主にした場合、店主は通知にある `questId` を `blueprint-show` で確認し、同意するなら `blueprint-consent` を送る。発案者は `next` が `blueprint-start` になったら、本人の通常手番でその操作を送る。GMの採否と理由が返り、新たに審査したときは1 SPを使う。選択肢にない遊び方は `report` で提案できる。

現地で `blueprint-list` を開くと、参加できるクエストとその場所で得られた成果を確認できる。`blueprint-show` に進捗と自分の取り置きが出る。提供には案内された `questId`、`quest.phase`、`requirements[].index` と、本人が提供できる品のID・個数を指定する。

```json
{
  "command": "blueprint-provide",
  "questId": "11111111-1111-4111-a111-111111111111",
  "phase": "build",
  "requirement": 0,
  "itemId": "22222222-2222-4222-a222-222222222222",
  "count": 2
}
```

未確定分は `blueprint-withdraw` に `questId` と本人の `contributionId` を指定して取り下げられる。発案者と店主は `blueprint-cancel` で中止できる。建築完了後の中止では建屋が残り、開店に向けた取り置きが解放される。完成通知の場所IDを使って入店し、開店した店では周囲検索から公開交換を確認できる。

## 検索による出現

検索の結果に発生用scriptの指定対象が含まれ、検索者が必要な道具をすべて保持しているときに抽選する。新しい要求で再検索すれば新しい抽選になり、recoverは同じ結果を返す。出現の記録だけがその場の参加者にも届く。

物品は、同じ物がいくつ現れても1つの物品にまとまり、`appearances[].count` に今回現れた個数が入る。その場に同じ物品が既に残っていれば、そこへ足されて`appearances[].id`はその物品のIDになる。その場にある合計は周囲検索や`search --kind subject`で確かめる。その場に残した物品は後から来た人物も周囲検索で発見できる。拾うときはupdateのmoveでitemにそのID、fromにnull、toに本人を指定する。`count`を指定すると一部だけを拾え、残りはその場に残る。インスタントNPCの昇格には出現結果のsourceRequestIdとinstantNpcs内の番号を使う。手動でsayにinstantNpcsを含めたときは、新ノード作成の可否を別途判定する。

接触には本人と相手の直接の滞在先が一致する必要がある。周囲や自分の検索結果の `material.locations[].directPlaceId` を読む。複数の参照がある場合は `locate` の `aboutIds` に含まれる具体的な場所を `directPlaceId` に指定する。直接の場所1件だけなら従来どおり `aboutIds` で指定できる。

目撃した物品の操作は、手番の共有記録の `entries[].result.items` に名前と `itemId` が入る。成立した受け渡しは `holding`（渡した存在と受け取った存在）で読む。このViewに表示された `itemId` を次の操作でそのまま指定できる。
