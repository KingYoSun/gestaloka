# 世界への申請

`gestaloka play --file <UTF-8のJSONファイル>`でPlayCommandを送る。CLIが要求IDを作成・保存する。返却を失った場合は`recover`で同じ要求を照合する。下記の識別子は実際に本人が取得したものへ置き換える。

ダイスを振る申請・判定の材料・エラーごとの原因は[ダイスの判定](dice.md)を読む。`text`や`basis`に書いた内容は記述として記録されるだけで、物を持つ存在は変わらない。物を持つ存在は`create`の`holder`と`move`の`to`で指定する。

## 時間差で受け取る申請

メモや物品の受け渡しは、期限を付けると不在の相手も後から判断できる。対象になる申請と受領手順は[相手が後から受け取るとき](sessions.md#相手が後から受け取るとき)を参照。

## 場所に公開する交換

登録した保管先に在庫を置いて交換条件を公開すると、店主が不在でも現地で買える。`offer` のJSON例と購入手順は[店に交換条件を出す](inventory.md#店に交換条件を出す)を参照。

## 抽選器を設定して引く

[抽選器で遊ぶ](draw.md)に、GM生成・固定表の設定、公開、抽選、補充の手順があります。

## 用途別の更新

`dependencies`には素材検索が返した依存版を渡す。`operations`は既存の内部処理を使い、受理した差分だけが原子的に確定する。

```json
{
  "command": "update",
  "text": "取得した場所へ移動する",
  "operations": [
    {
      "type": "locate",
      "subjectId": "本人のID",
      "text": "場所の説明",
      "aboutIds": ["直接滞在する場所のID"],
      "directPlaceId": "直接滞在する場所のID"
    }
  ],
  "dependencies": []
}
```

| type           | 引数                                     | 意味                         |
| -------------- | ---------------------------------------- | ---------------------------- |
| locate         | subjectId, text, aboutIds, directPlaceId | 本人または同行者の所在地     |
| create         | label, count任意, holder, basis          | 新しい物品。holderの物になる |
| move           | item, from, to, count任意, basis         | 受け渡し。toの物になる       |
| grant / revoke | person, storage。grantにはbasis          | 家・場所の保管先の登録       |
| learn          | person, text, basis, consumeSkillIds任意 | 技能の習得・発展・統合       |
| update         | id, text任意, count任意, basis任意       | 物品の呼称・個数、技能の内容 |
| remove         | id, count任意                            | 消費・破棄・技能の喪失       |

### 物の受け渡し

品物を渡す・売る・預ける・拾うときは `move` で持つ存在を変える。受け渡しの条件と売買のJSON例は[持ち物・保管・取引](inventory.md)を参照。

### 物品の個数

個数つきの品は `move` や `remove` に `count` を指定して一部だけを扱える。手持ちと保管先の使用枠、容量不足のときに渡せる個数は[個数と容量を確かめる](inventory.md#個数と容量を確かめる)を参照。

### ダイスの成功で減る物品

GMがダイスを設定する申請（新規作成、個数を増やす更新、対抗行動）では、GMが同じ判定で、成功したときに減る物品も決める。対象は本人が手に持つ物だけで、保管先に置いた物は減らない。応答の`outcome.setting.consumes`に、物品のID・呼称・減る個数が入る。成功すると申請と同じ確定で減り、失敗すれば減らない。申請自身が`operations`で動かす・減らす物品は、GMの判定からは外れる。新しい場所の`explore`では減らない。

### ダイスの失敗で残る状態

作成の判定と対抗の判定に失敗すると、GMの設定によってはもう一度ダイスを振り、ファンブルになると申請者本人に状態が残る。応答の`outcome.fumble`と`outcome.setting.fumble`で読める。残った状態には期限が付くことがある。扱いは[ダイスの判定](dice.md)の「判定で一緒に決まること」を参照。

### 物を使って何かを変える

塗料で壁を塗る、木材で柵を建てる、食材で料理するなど、手元の物を使って何かを変えたときは、**変わった結果の状態**を `changes` で申請する。使う物は `remove` で消さずに、手に持ったまま申請する。ダイスが成功すると、GM が手元の物から使った分を選んで減らす（`outcome.setting.consumes`）。

`remove` で物を消すだけの申請では、物が減るだけで、結果は記録されない。`text` に「壁を紫に塗った」と書いても、壁の状態は変わらない。

飲む・食べる・燃やすなど、使った後に何も残らないときは、結果の状態を作らずに `operations` の `remove` で減らす。ダイスは振らずに確定する。

```json
{
  "command": "update",
  "text": "手持ちの薬草茶を飲み干す",
  "operations": [{ "type": "remove", "id": "消費する物品のID", "count": 1 }],
  "dependencies": []
}
```

`count` を省くと、その物品が全部なくなる。

```json
{
  "command": "update",
  "text": "手に持つ青い塗料と刷毛で、家の柵を青く塗る",
  "changes": {
    "nodes": [
      {
        "id": "新しく作る状態のID",
        "kind": "script",
        "text": "家の柵は青く塗られている。"
      }
    ],
    "revisions": [],
    "edges": [
      {
        "id": "新しく作る関係のID",
        "kind": "status",
        "role": "content",
        "source": "家のID",
        "target": "新しく作る状態のID",
        "period": { "from": 0 }
      }
    ],
    "endEdges": ["当てはまらなくなった古い状態の関係のID"]
  },
  "dependencies": []
}
```

- 新しい状態のIDと関係のIDは、申請ごとに新しいUUIDを作る。
- 古い状態（「柵は白い」など）が残っていれば、`endEdges` にその関係のIDを入れて終える。家や場所の状態と関係のIDは、`search --kind subject --target <家のID>` で読める。
- 新しい状態を作る申請なので、ダイスで判定する。失敗すれば申請した変更は確定せず、物も減らない。
- 料理や工作には `operations` の `create` を使う。手持ちや現在地から必ず使う物は、単独申請の直下、または `create-batch` の各案に `"materials": [{"id": "物品のID", "count": 2}]` と書く。個数を省略すると1個、個数のない物品ならその現物を使う。自由入力で現物が特定できない案には `MATERIAL_ID_REQUIRED` が返るので、物品のIDを指定して申し込み直す。

### 時間をかけて物品を得る

その場にない物を取り寄せる、手間をかけて作る、育つのを待つなど、すぐには手に入らない物品は、かける時間を指定して申請できる。`update` に `waitMinutes`（実時間の分）を加える。世界の時間は実時間と同じ速さで進むものとして数える。

```json
{
  "command": "update",
  "text": "隣町の牧場からミルクを取り寄せる。銀貨で払い、荷車で2日かけて運んでもらう",
  "operations": [
    {
      "type": "create",
      "label": "ミルク",
      "count": 10,
      "holder": "本人または保管先のID",
      "basis": "隣町の牧場から取り寄せた"
    }
  ],
  "waitMinutes": 2880,
  "dependencies": []
}
```

- かける時間は、GMがダイスを設定する材料になる。時間をかけるほど成立しやすい申請では、かける時間に応じて判定が緩くなる。すぐに成立させるには無理がある物ほど、長い時間を指定する意味がある。`text` には、何をどう手に入れるかと、その時間で足りる理由を書く。
- 指定できるのは、物品の `create` だけを並べた申請に限る。`holder` に同席者を指定するなど、他の参加者の受領が必要な申請には指定できない。どちらも `WAIT_NOT_APPLICABLE` が返り、通常枠は使わない。
- ダイスは申請時に一度だけ振る。失敗すると何も作られず、通常枠を1回使う。成功すると、GMが選んだ代価（`outcome.setting.consumes`）が同じ確定で減り、応答の `arrival.dueAt` に物品が届く時刻が入る。
- 物品は届く時刻を過ぎてから、`holder` に指定した存在のもとに成立する。それまでは持ち物に現れない。届く予定は `search --kind self` の `arriving`（申請の文、物品の呼称と個数、届く時刻）で読める。人に約束するときは、この予定を確かめてから伝える。
- 届くと本人あての通知ができる。`gestaloka notices` で読む。届いた物品を人へ渡すには、`move` を申請する。

他の参加者の受領が必要な通常の申請は、同席者に判断が回る。本人と同行者の `locate` をまとめる例と承認・却下の結果は[いま一緒に移動する](sessions.md#いま一緒に移動する)を参照。

更新では`operations`の代わりに`changes`で自由な差分を申請できます。既存の状態を終えて新しい性質・関係を記録する場合にも使えます。対抗行動でも同じ二つの形式を使い、特定の行動の一覧には限定しません。

### 本人の呼称と状態を改める

本人の呼称と、本人についての状態（外見・性格・経歴などの記述）は、`update`の`changes`で改める。`operations`の`update`が扱うのは物品と技能だけで、本人や状態のIDを指定すると`BELONGING_NOT_RECORDED`が返る。

`search --kind self`の`material.states`で、状態ごとの本文（`node`）と本人との関係（`relation`）を読む。本文を改めるときは、`revisions`に取得済みの`id`・`kind`と新しい`text`を指定する。本人が状態の追加・改訂・終了を直接申請すると、GMが変更前の状態と申請内容を照合する。表記の訂正や成功済みの行動の反映はそのまま確定し、不確実な変化には同じ判断でダイスを設定する。

```json
{
  "command": "update",
  "text": "髪を短く切った",
  "changes": {
    "nodes": [],
    "revisions": [
      { "id": "状態のID", "kind": "script", "text": "黒い髪を短く切っている" }
    ],
    "edges": [],
    "endEdges": []
  },
  "dependencies": []
}
```

- 呼称を改めるときは、`revisions`に`material.node`の`id`と`"kind": "existence"`、新しい`text`を指定する。
- 当てはまらなくなった状態を終えるときは、`endEdges`に`relation`の`id`を指定する。
- 新しい状態を加えるときは、下記の「その他の作成」の形式で、どんな行動で何が変わるのかを書く。

## 新規作成

### メモノード

```json
{
  "command": "memo",
  "text": "見聞きした色や音を自由に並べるノート",
  "participants": ["関係する人物のID"],
  "dependencies": []
}
```

本文の用途は限定しない。メモは`kind: "script", type: "memo"`で保存し、関係する人物からの`has`で関連付ける。本人は自動で含まれる。本人以外には受領判断が回り、全員の受入後に確定する。参加者を指定しなければ本人だけに関連付ける。セッション外への申請は既存の受領と同じく即時エラーになる。

`search --kind memos`は、本人に関連付いた本文・人物・依存版を返す。更新は`update`の`changes.revisions`へ、取得済みのid・kind・typeと新しいtextを指定する。他の関係者の受領が必要になる。受領はメモを関連付ける手続きで、本文の主張をすべて世界の事実へ変換するものではない。

### その他の作成

自由な性質・関係を新しく記録する場合は、`command: "create"`、`text`、`changes`、`dependencies`を指定する。`changes`はnodes・revisions・edges・endEdgesを持つ既存のChange形式で、新規作成ではrevisionsとendEdgesを空にする。物品を持つこと・保管先・技能・所在地は用途別の更新を使う。自分で行動する人物や生き物は、`create`ではなく`say`の`--npc`で登場させる（[NPCの出現・昇格・同行](npcs.md)）。通常の発言と移動など規則で判断できる作成はGMを呼ばない。判断が残る作成では、GMが世界の基準に従ってダイスを設定し、サーバーが判定ごとに1回振る。物品の `create`、技能の `learn`、`say` の `instantNpcs` も同じ扱いになる。応答の `outcome` に成否・ダイス設定・出目が入る。判定に失敗した変更は確定しない。申請は行動として記録され、通常枠を1回使う。`say` の判定に失敗した場合は発言だけが記録され、`instantNpcs` は空で返る。同じ要求の再送は同じ結果を返す。

複数の技能を同時に習得する場合は、1件の `update` に技能ごとの `learn` を並べると個別に判定される。[技能の判定と製作を含む例](dice.md#技能を身につける)

異なる生成案をまとめるには、`play --file batch.json` で次の形式を送る。`proposals` の各案には `text` と、単発の申請と同じ `changes` または `operations` を指定する。最大5案で、探索は単発の `explore` を使う。素材は案の指定順に使う。先の案が失敗すれば次の案に使え、成功して残りが足りなくなった案には、ダイスを振らず `MATERIAL_SHORTAGE` を返す。

技能枠も案の指定順に数えます。先の案が成功して空いた枠は次の案に使えます。枠が足りない案は `SKILL_CAPACITY_EXCEEDED` になります。

```json
{
  "command": "create-batch",
  "dependencies": [],
  "proposals": [
    {
      "text": "端布から袋を縫う",
      "operations": [
        {
          "type": "create",
          "label": "布袋",
          "holder": "<本人のID>",
          "basis": "端布を縫った"
        }
      ]
    },
    {
      "text": "糸を編んで紐にする",
      "operations": [
        {
          "type": "create",
          "label": "組紐",
          "holder": "<本人のID>",
          "basis": "糸を編んだ"
        }
      ]
    }
  ]
}
```

`outcome.proposals` には申請順に結果が入る。技能を個別に判定した案は、その案の `proposals` で内訳を確認できる。製作に成功した案だけ生成物と素材消費が確定する。受領が必要な変更は従来どおり受領後に確定する。`spentSp` はその要求IDで消費したSPで、同じ要求を再送すると保存済みの結果が返る。全案が失敗しても新しく振れば1 SP、すべてが前の出目の再利用なら0 SP。`status` の `dailySp.remaining` が残量、`dailySp.resetsAt` が次の回復時刻である。日次の100 SPは日本時間の毎日0時に回復する。

GMがダイスを設定するときに読む材料は、世界の前提、申請の`text`と`changes`、申請者と申請が触れる対象の記録（状態と持ち物）である。セッションでの会話は渡らない。根拠にしたい物・人物・場所は、`changes`の関係で既存のIDを参照する。`text`には、何を使って何を得ようとするかを書く。運営者が表示を選んだ世界では、`status`の`creationCriteria`で世界の基準を申請の前に読める。

同じ手番でダイスに失敗した申請を、言い回しや細部だけ変えて出し直すと、同じ試みとして前回の設定と出目がそのまま返る。通常枠は1回使い、応答の`outcome.repeated`が`true`になる。別の対象や別の結果を求める申請は、これまでどおり新しく判定される。次の手番からは、同じ内容でも新しい試みとして判定される。この扱いは、運営者が判断モデルを設定した環境で働く。

## 新しい場所

まだ記録されていない場所へ行きたいときは、`explore`で場所の追加を申請する。通常の`create`とは別の操作で、接続元の場所が必須になる。

```sh
gestaloka explore --from <接続元の場所ID> --label <場所の呼び名> --text <場所の様子と、接続元からの行き方>
```

`play --file`で送る場合は次の形になる。

```json
{
  "command": "explore",
  "fromId": "接続元の場所のID",
  "label": "森の奥の沢",
  "text": "ぶー森の小道を奥へ進むと、浅い沢に出る。",
  "dependencies": []
}
```

接続元には、本人の現在の所在地にある場所を指定する。`search --kind self`または`surroundings`の`material.locations[].aboutIds`にあるIDが使える。離れた場所を接続元にはできない。

GMは接続元から見た妥当性でダイスを設定し、サーバーが一度だけ振る。応答の`outcome`に成否・ダイス設定・出目が入る。成功すると`placeId`に新しい場所のIDが返り、`update`の`locate`でそこへ移動できる。接続元と新しい場所には同じ記述が付き、どちらを`search --kind subject`で調べても、相手の名前とIDを`about`から読める。後から来た人物も同じ手がかりで行き来できる。どちらの場所に直接滞在していても、`search --kind surroundings`の`material.routes`に相手の名前とIDが出る。`routes`は移動先の手がかりで、載っていない場所へも、検索結果で受け取ったIDなら`locate`で移動を申請できる。新しい場所は、接続元にいる間も`search --kind subject`で調べられる。

既にある場所と同じ呼び名（`label`）では申請できない。`EXPLORE_NAME_TAKEN`が返り、メッセージに先にある場所のIDが入る。GMは呼ばれず、通常枠も使わない。その場所を`search --kind subject`で調べるか、別の呼び名で申請する。

失敗しても行動として記録されて通常枠を1回使い、場所は作られない。同じ要求の再送は同じ結果を返す。

## 受領を経ない対抗行動

```json
{
  "command": "oppose",
  "text": "相手が持つ品を奪おうとする",
  "operations": [
    {
      "type": "move",
      "item": "対象のID",
      "from": "今持っている存在のID",
      "to": "本人のID",
      "basis": "対抗行動"
    }
  ],
  "dependencies": []
}
```

本人の解釈や持ち物の破棄は通常の更新で扱う。対抗行動の前提となる対象と、それを持つ存在が記録と合わなければ失敗する。外界に作用する対抗行動の関係を構築できる場合はGMがダイスを設定し、サーバーが抽選して結果を保存する。出目と結果を返却から読み、失敗した同じ要求を再送しても振り直さない。

同席している出現個体（インスタントNPC）へ作用するときは、`operations`と`changes`の代わりに`effect`を指定する。`targetId`には同席者一覧にある個体のIDを入れる。

```json
{
  "command": "oppose",
  "text": "鳥に石を投げる",
  "effect": { "targetId": "個体のID", "state": "石が当たる" },
  "dependencies": []
}
```

個体への作用はダイスで判定する。一団の分離、残数や落ちた品の読み方、分かれた1体の昇格は[NPCの出現・昇格・同行](npcs.md)を参照。

同席しているプレイヤーやユニークNPCへの対抗行動が成功すると、GMが決めた変化後の状態（`outcome.setting.states`）が相手に記録される。傷を負わせる、縛るといった結果を `changes` に書かなくても、`text` と変更から読み取れる変化が残る。

運営者が死亡判定を有効にしている世界では、同席しているプレイヤーとユニークNPCも同じ判定の対象になる。対抗行動が成功し、GMが死亡と判定した人物（`outcome.setting.fatal`）は、セッションから外れて世界に設定された場所か本人の最初の所在地へ移る。本人が対象になった場合も同じで、移った先の単独のセッションで続ける。`search --kind self`で所在を確かめ、また話すには同じ場所で`contact`し直す。

## 設計図で建てる・開店する

公開テンプレートを選んで現地の設計図を記入すると、採用後はほかの人もクエストに材料を提供できる。申請例と参加手順は[テンプレート・設計図・クエスト](blueprints.md)を参照。

## 製作と現地での受け渡し

## 検索による出現

検索の結果に発生用scriptの指定対象が含まれ、検索者が必要な道具をすべて保持しているときに抽選する。新しい要求で再検索すれば新しい抽選になり、recoverは同じ結果を返す。出現の記録だけがその場の参加者にも届く。

物品は、同じ物がいくつ現れても1つの物品にまとまり、`appearances[].count` に今回現れた個数が入る。その場に同じ物品が既に残っていれば、そこへ足されて`appearances[].id`はその物品のIDになる。その場にある合計は周囲検索や`search --kind subject`で確かめる。その場に残した物品は後から来た人物も周囲検索で発見できる。拾うときはupdateのmoveでitemにそのID、fromにnull、toに本人を指定する。`count`を指定すると一部だけを拾え、残りはその場に残る。出現した個体との関わり方と昇格に使う記録は[NPCの出現・昇格・同行](npcs.md)を参照。
