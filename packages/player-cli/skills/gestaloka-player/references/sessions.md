# セッション・手番・受領とチーム

市場で友人に声をかけ、一緒に宿へ向かう場合を考える。**場所**は人物がどこにいるか、**セッション**はいま誰と会話と手番を共有しているかを表す。同じ市場にいても、別々のセッションで遊んでいることがある。**チーム**を組むと、別行動の後に同じ場所へ着いた仲間と再合流できる。

以下のコマンドは `gestaloka` に続けて実行する。

## 同じ場所で合流する

1. `status` で現在の手番を確認する。自分から遊び始めるときにセッションがなければ `start` する。
2. 自分の手番で `search --kind surroundings` を読み、相手と自分の直接の滞在先（`material.locations[].directPlaceId`）を確かめる。市場の入口と市場の中は別の場所になり得る。先に移動する場合は、`update` の `locate` で自分の所在を変える。
3. 同じ場所で `contact --target <相手の人物ID>` を送る。返った `result.actionable` と `result.actionMessage` で、自分が続けて動くか待つかを確認する。相手が離席中なら、合流後も自分の手番を続けられる。その間の発言や行動は相手の記録に残る。

`status --view joins` で同席者、手番の持ち主、合流の記録を読める。合流しても別行動になっても、本人のプレイ履歴は同じID（`sceneId`）で続く。各人の履歴には、発言した時に同じ場所で会話に参加していた分だけが残る。手番の途中で退出しても、そこまでに聞いた話は読み返せる。合流前に交わされた話は、居合わせた仲間に聞いてみよう。

## いま誰が操作するかを読む

`status` の `actorId` が本人なら、通常手番か受領判断を行える。同席の受領は、依頼が届いた時点から宛先全員が回答できる。新しい履歴が0件でも操作できる場合がある。

| 自分から見た状態                       | 次にすること                                                                                                                                                                                      |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 自分の通常手番                         | `search` で素材を調べ、`say` で話し、世界に残す変更は `play --file <JSON>` で申請する。`callsUsed` と `callsLimit` で通常枠を確認し、区切りがついたら `end-turn` で手番の結果を同席者と共有する。 |
| `receiving` があり、自分がいまの受領者 | `receiving.recipients` に本人が含まれ、`actorId` が本人であることを確認する。申請ID、本文、変更内容、期限を読み、`receive --application <申請ID> --accept` または `--reject` で判断する。         |
| 他の人物の手番・判断待ち               | `receiving` は他の人宛てのものも表示される。本人が操作できるという通知を待ち、起きたら `status` を読み直す。                                                                                      |

通常枠の初期値は1手番8回、通常の受領判断の初期期限は600秒。実際には `status` の値を使う。相手が手番の前から離席中なら順番を飛ばす。途中で離席したときは600秒まで復帰を待つ。`status --view wait` で残り時間を確認でき、期限内に戻れば同じ手番が続く。待受の接続方法は[外部botの実行環境と待機](runtimes.md)を参照する。

`status` は前回読んだ後の履歴を返し、CLIがインスタンス別に `nextCursor` を保存する。`entries[].payload.transition` には退出や手番終了の時刻が残る。先頭から読み直すには `status --after 0`、合流記録だけなら `status --view joins --after 0`、以前のプレイの履歴と終了結果を読むには `result --scene <履歴ID>` を使う。`--view wait` と `--view joins` は既読位置を進めない。

## 受領で手番が移り、申請者に戻るまで

ミオが自分の手番にレンへ贈り物を申請すると、通常手番の途中でレンに受領判断が回る。レンが承認し、ほかに受領者がいなければ品が移る。応答の `result.decision` はレン自身の判断の受付、`result.application` は申請全体の状態を示す。複数の受領者がいる物品やメモの申請は全員の承認で確定する。一人でも却下するか、未回答のまま期限を迎えたら申請は不成立になる。申請者は `status` の `receiving.progress` で各回答の件数を読める。

申請に付けた `dependencies` は申請の時点で確かめる。受領を待つ間に、その場の人の出入りなど申請者が検索で見た周囲が変わっても、受領は止まらない。渡す物の持ち主など、申請した操作が読んだ記録が承認までに変わっていた場合は、承認の時点で申請が却下として終わり、`result.application.code` が `WORLD_CHANGED` になる。同じ承認を繰り返しても成立しないので、申請者が対象を確認して申請し直す。

申請が終わり、ミオが残っていて通常枠もあれば、**元の手番を再開するのはミオ**。復帰時の `context.receiptResult` で結果を確認でき、却下した人物は `rejectedBy` に出る。ミオが枠を使い切った場合や退出した場合は、残った同席者の手番順に進む。操作結果の `endedTurn` と `turnHolder` でも次の手番を確認できる。

期限切れや申請関係者の退出で判断が終わると、回答待ちだった宛先の `notices` に内容と終了理由が届く。無関係の同席者が退出しても、未回答の宛先は判断を続けられる。通信の返答を失ったときは `recover --request <要求ID>` で同じ要求の受付結果を照合する。

## 相手が後から受け取るとき

同席していても、手番をスキップされる離席中の相手を宛先にした同席受領は、申請の時点で `RECIPIENT_AWAY` になる。

相手が不在なら、メモの新規作成・本文改訂、または物品の `move` だけの申請に、Zか `+09:00` のようなUTCとの差を付けたISO日時で期限（`deferredUntil`）を付けられる。メモを送るCLIは `memo --text <本文> --participants <人物ID> --deferred-until <期限>`。受け手は別のセッションで遊んでいる間も、プレイを終えた後も `applications` から内容を読み、`receive` で判断する。申請者は `withdraw --application <申請ID>` で取り下げられる。照会・受領・取り下げに通常枠は使わず、結果は `notices` で読める。[持ち物・保管・取引](inventory.md)

## いま一緒に移動する

市場から宿へミオ、レン、ハルの3人で移るなら、ミオの通常手番で、本人と同行者それぞれの `locate` を一つの `update` に書く。次の例のIDを検索した値に置き換え、検索で得た依存版を `dependencies` に入れて `play --file action.json` で送る。

```json
{
  "command": "update",
  "text": "市場を出て、二人を宿へ誘う",
  "operations": [
    {
      "type": "locate",
      "subjectId": "ミオのID",
      "text": "宿に入る",
      "aboutIds": ["宿のID"]
    },
    {
      "type": "locate",
      "subjectId": "レンのID",
      "text": "宿に入る",
      "aboutIds": ["宿のID"]
    },
    {
      "type": "locate",
      "subjectId": "ハルのID",
      "text": "宿に入る",
      "aboutIds": ["宿のID"]
    }
  ],
  "dependencies": []
}
```

所在の変更だけの申請は、全員が回答した時点か、受領期限に達した時点で確定する。レンが承認し、ハルが辞退するか期限までに回答しなければ、ミオとレンは宿に移って同席を続ける。ハルは市場に残る。同行の承認がゼロで未回答のまま期限を迎えたら、既定ではミオも市場に残る。`play --file action.json --depart-alone-on-timeout` で申請すると、その場合もミオだけが出発する。移動に複数の場所の参照を含めるときは、`directPlaceId` で直接の滞在先を指定する。

## チームで別行動し、再合流する

別々に買い物をして後で落ち合うなら、ミオが `team invite --target <レンのID>` で招待する。レンは `team status` で招待を確認し、`team join --team <チームID>` で承諾する。一つの世界で所属できるチームは一つ。

ミオが先に宿へ着き、後からレンが同じ宿へ着くと、レンはミオがいるセッションに自動で合流する。先着側の手番と受領判断はそのまま続く。移る側が受領判断に関わっていれば、その判断が終わってから合流する。隠密で移動した仲間とは、発見後に合流する。

| どこまで終えるか       | コマンドと結果                                                                                   |
| ---------------------- | ------------------------------------------------------------------------------------------------ |
| 今の手番を渡す         | `end-turn`。一人で遊んでいれば次も自分の手番。                                                   |
| チームを抜ける         | `team leave`。再合流のための所属を解き、同席中ならその場の会話を続けられる。                     |
| 今の同席者と別れて遊ぶ | `leave`。同席者とセッションを分けてプレイを続ける。                                              |
| 今回のプレイを終える   | `finish`。本人のプレイを終え、確定した履歴を受け取る。待機も終了する場合は `disconnect` を使う。 |
