# ダイスの判定

新しい物・性質・場所を世界に加える申請や、相手に作用する申請は、ダイスで成否が決まる。この文書では、ダイスを振る申請と振らない申請、判定の材料、申請の書き方、エラーごとに考えられる原因をまとめる。申請の完全な形式は[世界への申請](commands.md)を読む。

## ダイスを振る申請

| 申請                                                                | 判定の種類 |
| ------------------------------------------------------------------- | ---------- |
| `update` の `operations` にある `create`（物品の作成）              | 作成の判定 |
| `update` の `operations` にある `learn`（技能の習得）               | 作成の判定 |
| `update` の `operations` の `update` で個数を増やす・新しく付ける   | 作成の判定 |
| `create`、または `update` の `changes` で新しいノード・関係を加える | 作成の判定 |
| `say` の `--npc`（その場に人物や生き物を新しく登場させる）          | 作成の判定 |
| `explore`（新しい場所）                                             | 場所の判定 |
| `oppose`（受領を経ない対抗行動）で、他人や外界に作用する            | 対抗の判定 |
| `npc-action` と `oppose` の `effect`（出現個体への作用）            | 対抗の判定 |

次の申請ではダイスを振らない。規則と受領判断だけで決まる。

- `say` の発言と、世界を変えない行動の描写
- `locate`（移動）、`move`（受け渡し）、登録済みの保管先への `grant`・`revoke`、`remove`（消費・破棄）、個数を減らす `update`
- 本人の状態の本文を改める `changes.revisions` と、関係を終える `endEdges` だけの申請
- 本人の解釈だけを記録する申請（`interpret` の関係と、その本文の `script` だけ）
- `memo`
- 本人の操作範囲だけで済む `oppose`（成功として扱う）

ダイスを振る操作と振らない操作を一つの申請に並べると、申請全体を一度のダイスで判定する。失敗すると、ダイスを振らない操作も含めて何も確定しない。

## 判定の流れ

1. サーバーが申請の形式、対象の存在、依存版、所在の条件を確かめる。ここで外れると、ダイスを振る前にエラーが返る。通常枠は使わない。
2. GMが判定の設定を返す。中身は面の数 `sides` と、成功の上限 `successThrough` である。GMが決めるのは設定だけで、物語や追加の変更は作らない。
3. サーバーが1から `sides` までの出目を一度だけ振る。出目が `successThrough` 以下なら成功。
4. 成功すると、申請した変更と、GMが選んだ消費が同じ確定で記録される。失敗すると何も変わらない。行動としては記録され、通常枠を1回使う。

応答の `outcome` に `success`（成否）、`setting`（`sides`・`successThrough` など）、`roll`（出目）が入る。

### GMが読む材料

- 世界の前提（世界を作ったときの設定文）
- 世界の判定基準。運営者が表示を選んだ世界では、`status` の `creationCriteria` で申請前に読める。空欄なら既定の基準「材料から判断できる実現可能性を1d100のダイスの基準値で設定する」を使う。
- 申請の `text` と、申請が作る・変える内容（`changes`、または `operations` から組み立てた差分）
- 申請者と、申請が触れる対象の記録（状態と持ち物）
- 申請者が手に持つ物品（消費の候補）
- `waitMinutes` を付けた場合は、かける時間

セッションの会話は渡らない。説得や準備の経緯を判定に使ってほしいときは、`text` に書くか、根拠になる物・人物・場所を `changes` の関係で既存のIDとして参照する。

`explore` は世界の判定基準を使わず、接続元から見た妥当性を1d100で判定する。

### 判定で一緒に決まること

- **消費**: GMは同じ判定で、成功したときに減る物品を選ぶ（`outcome.setting.consumes`）。対象は申請者が手に持つ物だけで、保管先の中身は減らない。申請自身が `operations` で動かす・減らす物品は対象にならない。`explore` では減らない。
- **死亡**: 対抗の判定では、GMが成功したときに死亡する個体や人物も決める（`outcome.setting.fatal`）。プレイヤーとユニークNPCが対象になるのは、運営者が死亡判定を有効にしている世界だけである。
- **時間**: `waitMinutes` を付けた物品の `create` では、時間をかけるほど成立しやすい申請なら判定が緩くなる。成功すると、物品は `arrival.dueAt` を過ぎてから成立する。

### 出し直しと再送

- 同じ手番でダイスに失敗した申請を、言い回しや細部だけ変えて出し直すと、同じ試みとして前回の設定と出目がそのまま返る。`outcome.repeated` が `true` になり、通常枠を1回使う。対象か、得ようとする結果が違えば、新しく判定する。次の手番からは、同じ内容でも新しい試みとして判定する。この扱いは、運営者が判断モデルを設定した環境で働く。
- 返答を失ったときは `recover --request <ID>` で照合する。同じ要求IDの再送は保存した結果を返し、振り直さない。同じ要求IDで中身を変えると `REQUEST_CONFLICT` になる。

## 申請のパターン

### 物品を作って手に持つ

作った物は `holder` に指定した存在の物になる。本人の物として作るなら `holder` に本人を指定する。

```json
{
  "command": "update",
  "text": "流木と蔓で釣り竿を作る",
  "operations": [
    {
      "type": "create",
      "label": "釣り竿",
      "count": 1,
      "holder": "本人のID",
      "basis": "流木の枝に蔓を結んで作った"
    }
  ],
  "dependencies": []
}
```

### 本人の保管先に直接作る

`holder` に本人が登録した保管先（自宅など）や手に持つ箱を指定すると、作った物はそこに置かれる。

```json
{
  "type": "create",
  "label": "保存用の干し肉",
  "count": 5,
  "holder": "自宅のID",
  "basis": "台所で燻して作った"
}
```

### 持ち物の個数を増やす

`operations` の `update` で `count` を増やす。新しい物を得る申請として判定する。減らすだけなら判定はない。

```json
{
  "type": "update",
  "id": "物品のID",
  "count": 12,
  "basis": "畑でさらに収穫した"
}
```

### 技能を身につける

```json
{
  "type": "learn",
  "person": "本人のID",
  "text": "鑑定: 金属の材質と純度を見分けられる",
  "basis": "試金石とルーペで鑑定を重ねてきた"
}
```

### 中身を相手や場所に委ねる

祈りや贈り物のように、得る技能や物品の中身を本人が決めない申請では、`text`・`label` に委ねる相手と範囲を書く（例: 「泉の精が選ぶ、水にまつわる小さな技能を1つ」）。成功すると、GMが決めた本文で技能や物品が確定する。確定した本文は応答の `outcome.setting.decided` にあり、`search --kind self` でも読める。中身を自分で書いた申請は、書いたとおりに確定する。`create-batch` と `waitMinutes` を付けた申請では、GMは本文を決めない。

### 時間をかけて取り寄せる

物品の `create` だけを並べた `update` に `waitMinutes` を加える。書き方は[世界への申請](commands.md)の「時間をかけて物品を得る」を読む。

### 新しい性質や関係を記録する

`create`、または `update` の `changes` で、新しいノードと関係を申請する。保持・保管・技能・所在地は `changes` では書けない。`operations` を使う。

### 新しい場所

`explore --from <接続元の場所ID> --label <呼び名> --text <説明>`。接続元は、本人の現在の所在地にある場所に限る。

### 対抗行動

相手の物を奪う、相手に作用するなど、相手の受領を待たずに試みる行動は `oppose` で申請する。出現個体へ作用するときは `effect.targetId` に個体のIDを指定する。個体は同じ場所にいる必要がある。

## エラーと考えられる原因

エラーは判定の前に返る。通常枠は使わず、ダイスも振らない。

| コード                        | 考えられる原因と対処                                                                                                                                                                |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `TURN_REQUIRED`               | 本人の通常手番ではない。手番が終わった後に申請した。無操作の期限で手番が終わった。`status` で手番を確かめる。                                                                       |
| `WORLD_CHANGED`               | 検索してから申請するまでに、依存版に含めた記録が変わった。既に終わっている関係を `endEdges` に指定した場合も、このコードになる。`search` し直し、新しい `dependencies` で申請する。 |
| `REQUEST_CONFLICT`            | 同じ要求IDで中身の違う申請を送った。`play --file` は要求IDを自動で作るので、手で要求IDを付けた場合に起きる。                                                                        |
| `WAIT_NOT_APPLICABLE`         | `waitMinutes` を、物品の `create` 以外を含む申請や、`changes` の申請に付けた。`holder` に同席者を指定して受領が要る申請に付けた。                                                   |
| `DEFERRED_NOT_APPLICABLE`     | `deferredUntil` を、ダイスで判定する作成を含む申請に付けた。時間差の受領は、受領が要るメモか、物品の `move` だけの申請に使う。                                                      |
| `CREATION_ONLY`               | `command: "create"` に `revisions` や `endEdges` を入れた。既存の記録を改めるときは `update` を使う。                                                                               |
| `INTERNAL_OPERATION_REQUIRED` | `changes` に、物品を持つ関係（物品への `has`）、保管先・技能（役割つきの `has`）や所在地を書いた。`operations` の `create`・`move`・`grant`・`learn`・`locate` を使う。             |
| `SERIES_ADMIN_REQUIRED`       | 物品に `seriesId` を付けた。系列のある物品（通貨など）の個数を増やそうとした。どちらも管理者だけが行える。                                                                          |
| `TARGET_NOT_FOUND`            | 操作や関係の対象のIDが存在しない。短縮IDの写し間違いや、他のインスタンスの記録から拾ったIDが多い。自分の検索結果のIDを使う。                                                        |
| `NODE_EXISTS`・`EDGE_EXISTS`  | 新規に作るノード・関係のIDが既にある。`changes` の新しいIDは毎回新しく作る。                                                                                                        |
| `NODE_CHANGED`                | `revisions` に指定した既存ノードの種別（`kind`）が記録と違う。                                                                                                                      |
| `EDGE_NOT_FOUND`              | `endEdges` に指定した関係が見つからない。                                                                                                                                           |
| `CONNECTION_REJECTED`         | 関係の向きや種類が許されない組み合わせになっている（例: 状態の `content` の向きが逆）。                                                                                             |
| `BELONGING_NOT_RECORDED`      | `operations` の `update` に、持つ存在が記録されていない物や、本人・状態のIDを指定した。本人の呼称や状態は `changes` の `revisions` で改める。                                       |
| `HOLD_CHANGED`                | `move` の `from` が、物品を今持っている存在と違う。誰かが先に動かした。検索し直す。                                                                                                 |
| `HOLD_NOT_RECORDED`           | 持つ存在が記録されていない物に、`from` で持ち主を指定した。その場に落ちている物は `from: null` で拾う。                                                                             |
| `GROUND_ITEM_NOT_HERE`        | 本人がいない場所に落ちている物を拾おうとした。拾う先を本人以外にした。                                                                                                              |
| `STORAGE_NOT_HERE`            | 保管先や場所から離れたところで出し入れしようとした。`locate` でその場所へ移ってから申請する。手に持つ箱は、どこでも出し入れできる。                                                 |
| `STORAGE_NOT_REGISTERED`      | 他人が登録した保管先から物を取り出そうとした。取り出せるのは登録した人物だけなので、渡してもらう。                                                                                  |
| `REMOTE_RECEIVING`            | 受領が要る相手（物を渡す相手、物を持つ相手、保管先を登録した人物）が同じセッションにいない。同じ場所で `contact` して合流してから申請する。                                         |
| `RECIPIENT_AWAY`              | 同席受領の宛先に、手番をスキップされる離席中の同席者がいる。メッセージに名前とIDが入る。物やメモは `deferredUntil` を付けて申請し、同行の移動は離席中の人を外して申請する。         |
| `AUTHORITY_REQUIRED`          | 判断できる人物の記録がない物を相手にした。誰も持っていない箱など、場所でも保管先でもない存在への `move` で起きる。箱を手に持ってから出し入れするか、場所や保管先を使う。            |
| `NPC_UNASSIGNED`              | 受領が要るユニークNPCに、操作の担当が指定されていない。運営者に報告する。                                                                                                           |
| `INSTANT_NPC_NOT_PRESENT`     | `npc-action` に、同席していない個体を指定した。                                                                                                                                     |
| `NPC_ACTION_NOT_AVAILABLE`    | 出現を見ていない個体か、出現した場所とは別の場所にいるときに、その個体の `npc-action` を申請した。                                                                                  |
| `EXPLORE_SOURCE_REQUIRED`     | `explore` の接続元が、本人の現在の所在地にある場所ではない。                                                                                                                        |
| `EXPLORE_NAME_TAKEN`          | 同じ呼び名の場所が既にある。メッセージのIDを調べるか、別の呼び名で申請する。                                                                                                        |
| `UPDATE_REJECTED`             | `operations` の中身が記録と合わない。指定した個数の物品がない、物品以外（技能など）に `count` を付けた、`locate` の `aboutIds` に直接の滞在先がない、など。メッセージに理由が入る。 |

### エラーではない失敗

- `outcome.success: false` で `setting` と `roll` がある: ダイスの失敗。何も確定せず、通常枠を1回使う。
- `outcome.repeated: true`: 同じ手番で失敗した試みの出し直しと判定され、前回の結果が返った。
- `outcome.reason` が「対象と申請者の作用関係を構築できません」: 対抗行動の対象や、それを持つ存在が記録と合わないか、出現個体が同じ場所にいない。ダイスは振らない。

## 添え書き

申請の `text`、操作の `basis`、関係の `text` は、`say` と同じく記述として記録される。GMは判定の材料として読み、他の参加者も読めるが、世界の構造は変えない。

- `basis` に「貸しただけ」と書いても、返却は守られない。物は受け取った存在の物になる。
- `text` に「空き地に置く」と書いても、物品の所在は変わらない。物を持つ存在は `create` の `holder` か `move` の `to` で決まる。
- `text` に「村長の許可を得た」と書いても、受領判断の代わりにはならない。

申請の結果は、応答の `items[].holding` と、`search --kind self` の `belongings` で確かめる。
